# Jetpack dogfood plans: cards #2159, #2160, and #2164

This document plans only the three named cards. It does not reopen the signed
index or cache-admission designs, implement numeric suffixes, or extend the
dogfood target from `env.jet` to `devShells.full`.

## Shared constraints and frozen interfaces

Cards #2156 through #2158 own selection and admission. Treat these interfaces
from the sibling plans as frozen:

```rust
pub(crate) struct NixOutputRequest {
    name: String,
    store_path: String,
}

pub(crate) struct AdmittedNixObject {
    store_path: String,
    hangar_path: PathBuf,
    hangar_digest: String,
    direct_reference_digests: Vec<String>,
    upstream_proof_sha256: String,
}

pub(crate) struct AdmittedNixClosure {
    outputs: BTreeMap<String, AdmittedNixObject>,
    objects: BTreeMap<String, AdmittedNixObject>,
    closure_receipt_sha256: String,
}

pub(crate) fn admit_nix_closure(
    roots: &Roots,
    outputs: &[NixOutputRequest],
    offline: bool,
) -> Result<AdmittedNixClosure, StoreError>;

NixIndexClient::resolve(&IndexKey)
    -> Result<VerifiedIndexRecord, NixIndexError>;
```

The key handoff from #2158 is also frozen. Each selected logical output remains
in `ProducerRecord.facts` as `nix.output.<name>=/nix/store/...`.
`Realized.named_outputs` and `Realized.out` name Hangar objects. Direct
references are Hangar digests, and following the closure graph reaches every
object in `AdmittedNixClosure.objects`. The package producer connects the
signed index proof to #2156's signed cache proof and complete closure receipt.
Projection must consume those stored facts and graph edges; it must not call
the index or cache again.

The audit measured separate gaps for evaluation, substitution, and execution
(`docs/audits/jetpack-native-nixpkgs-2026-08-24.md:11-18,30-38`). This plan
keeps those boundaries:

```text
#2157 selects the exact output
    -> #2156 verifies and admits its complete closure
    -> #2158 records one connected Hangar graph
    -> #2159 projects only that verified graph for execution
    -> #2160 proves the real repository environment end to end
```

The real-cache evidence is not a fixture. The audit fetched the 657-byte
`axp6...ripgrep-15.2.0` narinfo from `cache.nixos.org`; it names zstd NAR bytes,
the glibc, pcre2, and GCC-library references, and a
`cache.nixos.org-1` signature
(`docs/audits/jetpack-native-nixpkgs-2026-08-24.md:152-187`). The sibling plan
records the exact body and an independent OpenSSL Ed25519 verification, plus a
negative mutation result
(`docs/plans/jetpack-dogfood/plan-2157-2158.md:36-81`). The current Nix manual
confirms that `References` is the direct store-path list and `Sig` may occur
more than once in a narinfo, and the current documented default public key is
`cache.nixos.org-1:6NCHdD59X431o0gWypbMrAURkbJ16ZPMQFGspcDShjY=`:

- <https://nix.dev/manual/nix/2.35/protocols/binary-cache/narinfo.html>
- <https://nix.dev/manual/nix/2.34/command-ref/conf-file.html#conf-trusted-public-keys>

The planning sandbox could resolve those official documentation pages but
could not resolve `cache.nixos.org` for a fresh direct fetch. Therefore the
captured live body above is the planning evidence, and the #2158/#2160 online
proof must fetch and verify the real narinfo again before either card closes.
No test may replace that fetch with a seeded Hangar object.

At plan time, `crates/jetpack/src/Shell.rs` and
`crates/jetpack/src/Store.rs` have unrelated uncommitted writers. A #2159
worker must get explicit ownership or wait for those edits to integrate before
writing. This is a shared-tree start condition, not a design choice.

## Card #2159 — host-store-independent closure projection

### Current evidence

- `CacheLease` stores a list of logical Nix paths and local sources, and the
  shell reads that list (`crates/jetpack/src/Store.rs:1213-1249`, planning
  baseline commit `f599e519a`; `crates/jetpack/src/Shell.rs:190-212`).
- `nix_store_projection_for_entry` reads only `nix.output.*`. It maps `out` to
  the private lease snapshot and other named roots to Hangar objects. It does
  not traverse `ClosureGraph::closure`
  (`crates/jetpack/src/Store.rs:1704-1764`). The graph already supplies direct,
  transitive, and root-inclusive closure traversal
  (`crates/jetpack/src/Store/Closure.rs:530-565`).
- The Linux launcher finds host `unshare`, `mount`, and `sh` by absolute path
  (`crates/jetpack/src/Shell.rs:216-238`). It then mounts an overlay whose
  lower layer is the host `/nix/store`; the comment explicitly defers an exact
  closure (`Shell.rs:261-297`). A missing transitive loader or library can
  therefore survive successful substitution as an execution failure.
- The non-Linux arm returns an uncoded I/O error
  (`crates/jetpack/src/Shell.rs:422-437`). This does not meet the explicit
  diagnostic criterion.
- `ClosureObject` records the Hangar digest, local path, and whether the object
  is external (`crates/jetpack/src/Store/Closure.rs:183-188`). The package
  record supplies output roots and direct reference edges
  (`Store/Closure.rs:437-455`). #2156/#2158 add one Nix producer record per
  admitted object, so the logical path can be recovered without another
  network lookup.

### Settled projection design

For one lease, construct a sorted map from every logical `/nix/store/<name>` in
the recorded root-inclusive closure to exactly one Hangar path. The root `out`
maps to the already sealed private lease snapshot. Every other digest maps to
its immutable `hangar/objects/<digest>` node. Recover its logical store path
from that object's decoded Nix producer `nix.output.*` fact. Reject a missing
fact, a digest/path disagreement, an external object, a non-regular source, a
logical path outside `/nix/store`, or two different sources for one logical
path. Do not omit a bad object and continue.

On Linux, enter a rootless user and mount namespace, mount a new tmpfs at
`/nix`, create an empty `/nix/store`, and bind each exact map entry read-only at
its logical path. There is no overlay and no lower directory. Open the launcher
helpers and target executable before hiding `/nix`; continue to pass them by
`/proc/self/fd` through the existing `inherited_tool_path` seam. The kernel can
then open an ELF `PT_INTERP` path such as the glibc loader at its original
logical store path, and that loader can resolve RPATH/RUNPATH libraries from
the same projected closure. The only `/nix/store` nodes visible to the child
are the map entries whose source paths are Hangar-owned.

The product supports this projection only on Linux hosts that provide
unprivileged user/mount namespaces, `/proc/self/fd`, and the absolute helper
tools already required by the implementation. All other hosts fail with
E1351. They do not run the unprojected Hangar executable and do not inherit a
host store.

### What not to do

- Do not keep the host `/nix/store` as an overlay lower layer, even read-only.
- Do not run an unprojected Hangar path when namespace setup fails.
- Do not copy only the selected output or direct references. Project the full
  root-inclusive graph recorded by #2156/#2158.
- Do not shell out to `nix`, `nix-store`, `curl`, or `wget`. `unshare`, `mount`,
  and `sh` are projection mechanics, not substitution or selection.
- Do not seed Hangar in a test. In particular, do not call or copy
  `realized_fixtures`/`seed_hangar_object` from
  `tests/support/jetpack_fixtures.rs:241-301`.
- Do not pin a per-package JSON closure map in product code or tests. Logical
  paths come from verified producer facts and graph records.
- Do not add an AOT-only, Linux-silent, or host-store fallback. Unsupported
  means E1351 and no child execution.

  `clippy`, `rustc`, `gcc`, `clang`, `lld`, `nodejs_22`, `nixfmt`, `ripgrep`,

  measured 0/20; the 0/22 default and 0/48 Linux-full figures are separate
  denominators, not extra scope for this card
  (`docs/audits/jetpack-native-nixpkgs-2026-08-24.md:68-89`).
- The current `.jet/lock` contains only `cargo` and no locked source-channel
  record (`.jet/lock:1-14`). It cannot be the dogfood input until #2155 and
  #2158 regenerate it canonically for all 20 attrs.
- `compose_env` walks `plan.refs` in order and appends each lease after
  realization (`crates/jetpack/src/CLI/trust_env_build.rs:176-286`).
  `Env::composed_path` deduplicates wrapper/bin directories while preserving
  first occurrence (`crates/jetpack/src/Shell.rs:92-118`). The gate must test
  these facts through the actual child PATH, not only repeat the unit logic.
- `hangar du` currently measures only each package's primary output with file
  `metadata.len()`, skips symlinks, and never walks transitive graph ownership
  (`crates/jetpack/src/Store/Closure.rs:21-125`). Its JSON sums those primary
  values into one `bytes` number
  (`crates/jetpack/src/CLI/package_hangar_vendor.rs:345-440`). The existing
  test proves only source-built object counting
  (`tests/jetpack_engine.rs:7876-7910`). That cannot reconcile a shared Nix
  closure.
- The owner acceptance sentence is exact: a fresh writable Hangar, empty
  ambient tool path, no `/nix/store`, no fixture directory, and no `nix`
  executable must cold-resolve, verify, store, execute, restart offline, and
  report exact disk use
  (`docs/audits/jetpack-native-nixpkgs-2026-08-24.md:130-140`).

### Settled gate shape

Add one Linux integration test that uses this repository's checked-in
`env.jet` and regenerated `.jet/lock`; it must not copy the 20 attrs into a
fixture project. The parent creates a fresh `JETPACK_ROOT` and Cargo target
below `$HOME/.cache/jet-test-scratch`. It enters #2159's rootless namespace,
where `/nix/store` is absent before launch. Every Jetpack process is invoked by
absolute path after `env_clear`; its ambient `PATH` is the empty string,
`JETPACK_FIXTURES` is absent, and a direct `Command::new("nix")` probe returns
`NotFound`.

The online run uses the production #2157 signed index and real Nix cache. It
executes a host-linked test child through `jetpack env`. That child records
its PATH and the resolved executable for all 20 probes. The test then performs
a real `cargo build --locked --bin jet` and a targeted
`cargo test --locked --test exact_number_tiers` through separate `jetpack
enter` processes. A new process repeats every probe, build, and targeted test
with Jetpack `--offline` inside a network namespace with no configured
interface. The second run must make zero index/cache requests and produce the
same Store receipts and command identities.

`hangar du --json` reports physical allocation for the root-inclusive closure,
not NAR sizes or summed per-package estimates. Each Hangar object is counted
once. An object reached by one package is `unique_bytes`; an object reached by
two or more package roots is `shared_bytes`; `closure_physical_bytes` is their
checked sum. The command explicitly excludes Store metadata, receipts, index
files, Cargo target output, and scratch from the closure total. On Unix,
physical allocation is `st_blocks * 512`, deduplicated by `(st_dev, st_ino)`
without following symlinks. On hosts where physical allocation is unavailable,
JSON reports `closure_physical_bytes: null` and the human command says that
physical closure use is unavailable; it never substitutes logical length.

## Card #2164 — numeric literal and Decimal defects

### Current evidence

- An untyped integer literal adopts an expected fixed-width integer carrier
  (`crates/jet-sema/src/Sema/CheckerInfer/expr.rs:2125-2163`). The decimal
  literal path also already adopts `Float` or `F32` when `expected_type`
  reaches it; otherwise it rewrites the literal to exact `Decimal`
  (`expr.rs:2165-2189`).
- Direct-call argument inference forwards expected type for Move parameters,
  functions, `IntN`, `F32`, inline ranges, named/optional types, and core views,
  but omits ordinary `Type::Float`
  (`crates/jet-sema/src/Sema/CheckerInfer/calls/direct_calls.rs:1663-1698`).
  That missing carrier is the `takes(3.4)` defect. The literal inference seam
  itself already has the required behavior.
- `type_fix_hint` has only Int/Float special cases. Its fallback repeats
  `want.show()` (`crates/jet-sema/src/Sema/Diagnostics.rs:198-246`), so E0112
  never names `Float{3.4}`. `Type::show` calls Float “a decimal number” and F32
  “a 32-bit decimal number”
  (`crates/jet-foundation/src/AST/types.rs:2127-2133,2211-2215`).
- The shared evaluator first tries
  `Comptime::display_core_pure_value`, then structurally renders unhandled
  values. The structural fallback produces the observed
  `Decimal { negative: false, digits: "34", scale: 1 }`
  (`crates/jet-codegen/src/Codegen/TIR/eval/exprs.rs:10454-10479,10606-10610`).
  `display_core_pure_value` handles other exact numeric carriers but omits
  Decimal (`crates/jet-comptime/src/Comptime/CorePureParity.rs:633-681`). AOT
  and web already have Decimal numeric rendering, so the missing shared pure
  display branch is the narrow I9 repair.
- `tests/exact_number_tiers.rs:11-22,49-239` already proves exact-number sema,
  TIR, AOT, default JIT, interpreter, comptime, REPL, JS, and Wasm behavior. It
  does not pass a bare decimal literal to a Float parameter or interpolate a
  bound Decimal.

### Settled correctness design

Pass `Type::Float` as the expected type for a direct-call Float parameter. The
existing literal inference then settles only that literal as approximate
Float. A bare binding such as `x :: 3.4` remains exact Decimal, and
`Float{3.4}` remains the explicit spelling when no expected type exists. No
implicit conversion is added for an already bound Decimal value.

When E0112 rejects a real Decimal value where Float is required, call Float an
“approximate binary number,” call Decimal an “exact base-10 number,” and give
the working repair: `write the literal as Float{3.4}, or keep Decimal on both
sides`. Render Decimal through `CtDecimal::to_string_rep()` in the shared pure
display seam before structural fallback.

This is independent of D-LITCARRIER1. A later suffix implementation would set
an explicit carrier at the lexer/parser/literal node before the same
`Expr::Float` inference branch. This card does not add, reserve, parse, or
document a suffix.

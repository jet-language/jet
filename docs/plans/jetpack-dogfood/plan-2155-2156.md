# Jetpack dogfood implementation plan for cards #2155 and #2156

This plan covers only the resolver/diagnostic defect in #2155 and native Nix
binary-cache closure admission in #2156. Provider/index integration, projection,
and full repository dogfooding remain #2157, #2158, and later cards.

## Planning basis

- `card show 2155` has no structured exit criteria. Its body records two defects.
  This plan closes only defect 1, the `cargo@default` E1317 blocker. Defect 2 is
  the E1272 realization gap owned by #2156 and #2158.
- `card show 2156` has five criteria. The proof table below repeats them
  verbatim and maps each to named tests.
- The audit requires every proof to use a fresh Hangar, no provider fixture
  directory, a controlled `PATH`, and no useful host `/nix/store`
  (`docs/audits/jetpack-native-nixpkgs-2026-08-24.md:450-456`). It rejects an
  installed Nix, pre-seeded fixture, host-store lower layer, and hand-pinned
  package path as closing proof (`docs/audits/jetpack-native-nixpkgs-2026-08-24.md:481-483`).
- The already-landed #2155 regression test is
  `declared_source_package_named_like_provider_resolves_as_package`
  (`tests/jetpack_engine.rs:3513-3530`). The existing compiled test binary was
  run while preparing this plan and reported:

  ```text
  running 1 test
  test declared_source_package_named_like_provider_resolves_as_package ... ok
  test result: ok. 1 passed; 0 failed; 160 filtered out
  ```

  Do not add a duplicate test.
- A direct live-cache reproduction was attempted on 2026-08-24, but this agent
  sandbox returned `curl: (6) Could not resolve host: cache.nixos.org`; an
  unsandboxed retry was not approved. The audit's captured upstream artifact is

## Card #2156 — native Nix binary-cache closure admission

### Fixed design

Keep the current Jet cache format and the standard Nix cache format as separate
trust protocols. `NarInfo` currently serializes Jet HMAC facts and assumes one
uncompressed hash (`crates/jetpack/src/Store/Nar.rs:137-203`); weakening it to
mean two protocols would make both harder to audit. Add a standard-cache model
named `NixNarInfo`, then share only the safe NAR decoder, hash utilities, native
transport, Hangar object layout, closure journal, and receipts.
Reuse `ed25519-dalek`: it is already the one ratified external dependency in
`crates/jetpack/Cargo.toml:28-30`, and Jetpack already verifies an Ed25519
receipt at `crates/jetpack/src/Store.rs:2822-2843`. Do not add another signature
library.

The crate-private handoff to #2158 is one engine interface in a new
`crates/jetpack/src/Store/NixCache.rs` module:

```rust
pub(crate) struct NixOutputRequest {
    pub name: String,
    pub store_path: String,
}

pub(crate) struct AdmittedNixObject {
    pub store_path: String,
    pub hangar_path: PathBuf,
    pub hangar_digest: String,
    pub direct_reference_digests: Vec<String>,
    pub upstream_proof_sha256: String,
}

pub(crate) struct AdmittedNixClosure {
    pub outputs: BTreeMap<String, AdmittedNixObject>,
    pub objects: BTreeMap<String, AdmittedNixObject>,
    pub closure_receipt_sha256: String,
}

pub(crate) fn admit_nix_closure(
    roots: &Roots,
    outputs: &[NixOutputRequest],
    offline: bool,
) -> Result<AdmittedNixClosure, StoreError>;
```

`outputs` preserves the selected named-output map from #2157. `objects` is keyed
by full upstream store path and includes selected outputs plus every transitive
reference. `upstream_proof_sha256` identifies the canonical verified narinfo
proof; `closure_receipt_sha256` identifies the one connected receipt committed
for the full batch. #2158 may convert the selected output results to `Realized`;
it must not refetch, reverify, or rebuild closure edges. `offline = true` permits
only already-verified complete Hangar reuse. The synchronous function owns the
entire transaction.

Production configuration is private to `NixCache.rs`: default to
`https://cache.nixos.org` and its official key. A paired
`<JETPACK_ROOT>/config/nix-cache-v1.endpoint` and
`<JETPACK_ROOT>/trust/nix-cache-v1.ed25519.pub` may replace both together for an
operator or loopback test; reject a lone file. Permit HTTP only for a loopback
host. Unit tests construct the private `NixCacheClient` directly instead of
expanding the provider-facing API.

### Canonical Nix signature fingerprint

Implement `NixNarInfo::fingerprint(store_dir: &str) -> Result<Vec<u8>,
NixCacheError>` exactly as Nix's
[`ValidPathInfo::fingerprint()`](https://github.com/NixOS/nix/blob/master/src/libstore/path-info.cc#L44-L50):

```text
1;<StorePath>;<NarHash>;<NarSize>;<full-reference-1>,<full-reference-2>,...
```

Byte rules:

1. Use ASCII `1;`, then the exact full `StorePath`, semicolon, `NarHash`
   normalized from its decoded 32 bytes to Nix's canonical
   `sha256:<52-character-Nix-base32>` spelling, semicolon, base-10 `NarSize`
   with no leading sign or padding, semicolon, then references joined with the
   single byte `,`. Do not preserve an alternative accepted hash spelling in
   the signed message; Nix's implementation renders `HashFormat::Nix32`.
2. Narinfo `References` are space-separated store basenames. Validate each as
   one store-path basename, prefix it with the cache's `StoreDir`, insert the
   full paths into a `BTreeSet`, and join the resulting sorted full paths.
   Reject a duplicate instead of silently deduplicating it. An empty set leaves
   the final semicolon as the final byte.
3. Do not append a newline or NUL. Field order in the `.narinfo` file does not
   affect the fingerprint. `URL`, `Compression`, `FileHash`, `FileSize`,
   `Deriver`, and `CA` are not signed by this fingerprint.
4. Parse `Sig` as `<key-name>:<standard-padded-base64>`. Decode exactly 64
   signature bytes. Parse a configured public key as
   `<key-name>:<standard-padded-base64>` and decode exactly 32 key bytes. Verify
   Ed25519 directly over the fingerprint bytes with `ed25519-dalek`; do not
   prehash. Accept the narinfo if at least one well-formed signature verifies
   under a trusted key with the same key name. Reject it if none does.

The signature/parser source is Nix
[`path-info.cc`](https://github.com/NixOS/nix/blob/master/src/libstore/path-info.cc#L115-L130),
the [narinfo protocol](https://nix.dev/manual/nix/2.35/protocols/binary-cache/narinfo.html),
and Nix's
[`local-keys.cc`](https://github.com/NixOS/nix/blob/master/src/libutil/signature/local-keys.cc).
Pin this real `cache.nixos.org` vector in a Rust test:


### What not to do

- Do not shell out to `nix`, `nix-store`, `curl`, `wget`, `zstd`, `xz`,
  `bzip2`, `gzip`, or `openssl` from the native Nix admission path or its tests.
- Do not use `tests/support/jetpack_fixtures.rs::realized_fixtures` or
  `seed_hangar_object`; those functions pre-seed Hangar output and are exactly
  why existing provider tests can pass without substitution
  (`tests/support/jetpack_fixtures.rs:241-301`).
- Do not read, mount, bind, copy, or use a host `/nix/store`. Treat signed Nix
  store paths only as cache identifiers and provenance.
- Do not require an already-known Hangar `StoreEntry`; that is the current
  remote-cache limitation at `Store/Cache.rs:554-561,669-683` in the planning
  worktree.
- Do not put closure fetching in `Provider.rs` or leave
  `Realized.references` empty. #2158 owns the provider mapping; #2156 returns a
  complete graph.
- Do not buffer a whole compressed NAR, whole unpacked NAR, or whole regular
  file. Do not preserve the 1-GiB byte-buffer cap as the production streaming
  policy.
- Do not verify `FileHash` against unpacked bytes or require it to equal
  `NarHash`. Verify compressed and unpacked layers independently.
- Do not verify Nix's signature over Jet's HMAC narinfo text, sorted field
  lines, JSON, a trailing newline, or a prehash. Use the exact fingerprint
  bytes above.
- Do not follow an unsigned absolute URL or cross-origin redirect from
  narinfo.
- Do not publish the root, any receipt, or any closure record before every
  transitive reference is present and verified.
- Do not make per-package JSON pins or the signed #2157 index a substitute for
  recursive standard-cache admission. The index discovers store paths; this
  card proves and admits their bytes.
- Do not add a second HTTP stack, async runtime, general scheduler, codec
  plugin abstraction, compatibility parser, or optional unsafe fast path.

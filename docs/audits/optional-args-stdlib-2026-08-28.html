JET / STDLIB DESIGN STUDY

Optional parameters vs sibling methods — Jet stdlib API-shape study (2026-08-28)

One policy question: when should a single root operation expose named options, and when should Core keep separate sibling methods?

01

The question

The owner proposes: instead of sibling methods sharing one signature shape, ship one root method with a great default for the most common operation, taking an optional customization parameter—for example, an enum for First/All. Namespace stays small, there is only one method to find, and the options are discoverable in the signature. Siblings stay justified when signatures genuinely differ.
02

What Jet already ratified

Call binding

D-CALLPOS1=A (ratified 2026-08-19, card #2042): bare call arguments fill left to right when deterministic; DEFAULTS FILL AFTER SUPPLIED ARGUMENTS; named arguments deconflict.

Default spelling

Parameter and field declaration defaults spell with braces: param: Type{default} (D-CHOOSE-FNBODY1 lineage).

Option surface

Regex replacement uses named sibling methods: replace means all matches and replace_first means at most one.

Tier-0 restriction

Comptime/generic-module VALUE parameters explicitly forbid defaults and named arguments. This policy can cover only ordinary runtime functions and methods.

Mechanism exists. Zero new syntax needed. fn replace(pattern: String, with: String) String and fn replace_first(pattern: String, with: String) String Call sites: s.replace(p, w) and s.replace_first(p, w).

04

Design analysis

What root + options buys

  • One discoverable name per operation; the signature shows the whole option space.
  • LSP hover and autocomplete teach available modes.
  • No combinatorial name explosion: the codec matrix drops from 24 names to 3.
  • Beginner call stays ceremony-free: s.replace(p, w).
  • Expert choice is named by the method: replace_first makes the scope visible at the call site.
  • Matches Python (re.sub count=) and Swift (labeled parameters + enums). Rust uses siblings because Rust lacks default arguments—a constraint Jet does not have.

Where it breaks down

  • The default is invisible at call sites. For dangerous variants such as zip length policy, the ratified verdict chose verbs precisely to force visibility.
  • Enum-option APIs need excellent diagnostics for the wrong enum and a missing label.
  • Options that change the result type—strict vs lossy decode—do not fit one signature cleanly. That is the honest sibling boundary.
  • Options can hide combinatorial semantics inside one body. Testing surface does not shrink; the same matrix remains.
Policy boundary: use an options enum when subject and result shape are identical and every mode is safe. Keep siblings when the result type changes, when a mode is a safety cliff the call site must spell, or when signatures genuinely differ.

06

Decision routing

Owner decision ratified
  • Policy ballot D-STDLIB-OPTPARAM1 on Tower card #2322 ratifies one root method with a safe default and named options.
  • D-REGEXREPL1 (#2304) now uses the root + options shape; D-BYTESDECODE1 (#2297) remains a separate fallibility decision.
  • Ratified D-ZIPLEN1=D / D-ZIPPAD1=E remain law unless the owner explicitly amends them. Greenfield migrations delete retired sibling spellings; no alias is retained.
  • Card #2310 (byte codec matrix) can now apply the same policy; it is the largest immediate beneficiary.

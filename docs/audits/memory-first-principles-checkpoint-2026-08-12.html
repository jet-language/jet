RATIFIED · D-MEM-COPYSEM1

Storing a view: the store means the copy.

Final ruling: a store of a read-only view means a copy — a language semantic, not an injection. Nothing is written into your file; the store behaves exactly as if you typed ~, on every tier. Mutable views (ViewMut) are never auto-copied — copying one would silently break write-back — so they keep today's error. #Policy(gc) stays exactly what you designed: the one-line explicit opt-in for zero-copy keep-alive.

fn run() {
    a :: "alpha:1"

The runtime as a linter — and one command to make it unnecessary.

Your framing, adopted wholesale: anywhere the runtime had to step in is a place the code isn't statically memory-safe yet — so list those places, and give one command that repairs them. RATIFIED · D-CONC-FREEZE1

Four tasks read one asset table.

One program, twice. Today the only legal spelling wraps the table in Shared and pays a lock on every read. Proposed: freeze it once; the compiler then allows the bare capture because frozen data can never race. Shared is untouched — it remains the right tool for data that genuinely mutates concurrently.

today — the only legal spelling (P09c shape)✓ compiles; lock per read
struct Assets { names: [String] }

fn render(a: Shared<Assets>, id: Int) => String {
    a.read(v => v.names[id])   // lock taken on EVERY read
}

fn run() {
    assets :: Shared.new(Assets.{ names: ["sword", "shield"] })
    task.group g {
        r :: task.all { render(assets, 0), render(assets, 1) }
        print(r)
    }
}
The data never mutates, but the lock doesn't know that. Eight render tasks × every read = contention for nothing, and the wrapper infects the signature. Note: this Shared.new/.read spelling is what the shipped binary runs (probe P09c); ratified D-CONC-SHARE1 replaces it with shared expr + plain field access. Lexical groups can already borrow provably non-overlapping reads (D-TASKBORROW1) — freeze covers sharing past that proof and past the group.
ratified direction — unbuilt, lands with #1891proposed
struct Assets { names: [String] }

fn render(a: Assets, id: Int) => String {
    a.names[id]                // plain read — no lock exists to take
}

fn run() {
    assets :: freeze(Assets.{ names: ["sword", "shield"] })  // (proposed)
    task.group g {
        r :: task.all { render(assets, 0), render(assets, 1) }  // bare capture legal BECAUSE frozen
        print(r)
    }
}
Delete the wrapper, delete the closures, delete the lock. freeze(x) makes the value deeply immutable forever; sharing immutable data across tasks is race-free by definition, so the E1101 capture rejection no longer applies to it. Writing to a frozen value is a compile error.

Same shape, second verb: hand a batch to one worker.

today — probed P09 (E1101)✗ plain capture rejected
fn run() {
    job := build_batch()
    task.group g {
        done :: task.all { process(job) }   // ✗ E1101: task may not
    }                                        //   capture mutable local
}
Correct rejection, no good exit: today you wrap job in Shared (a lock nobody else will contend) or copy it. The one thing you meant — "it's yours now" — has no spelling in a capture.
ratified direction — unbuilt, lands with #1891proposed
fn run() {
    job := build_batch()
    task.group g {
        done :: task.all { process(^job) }  // ^ = give — task owns the batch (proposed)
    }
    // `job` is gone here — the same rule ^ already has everywhere else
}
^ means in a capture exactly what it means at every callsite today. Use job after the handoff and you get the existing E0121 use-after-move error, verbatim.
Delta. Both panes, both stories: same program, one marked line of difference. The rule set after the change: give it (^), freeze it (freeze), or lock it (Shared) — and the compiler tells you which one your capture needs.
Ratified: "i accept your proposals" — D-CONC-FREEZE1=A. freeze + ^-captures adopted; Shared stays for shared-mutable. implementation plan #1891.
RATIFIED · D-MEM-GUARANTEE1

Wrapped raw pointers: an opt-in fence, not an ambient mode.

Your instinct — tracked "smart" pointers for untrusted code — is real (Fil-C ships it for C). It cannot be ambient: it goes blind when an address crosses to C, the OS, or hardware, costs 1.5–4× per pointer op, and would give one #Unsafe block two meanings. Final ruling: an explicit trust dial, decoupled from gc — gc buys lifetime convenience, never safety; the prover already guarantees safe Jet with gc off.

proposed — per-dependency containmentopt-in, priced, visible
# package.jet — the ratified policy shape (D-PACKAGE-POLICY-SCOPE1, tighten-only)   (proposed keys)
policy: .{
    contain: ["libxml"],   # fence just this dep — it pays 2–4×, your code pays nothing
}
# harden: true = the total switch: sentries stay in release AND every dep is contained —
# with harden on, no row below may read TRUSTED

$ jet inspect guarantees
your code            proven      compile time
#Unsafe gates (2)    watched     sentries (dev always; release via harden)
libxml (contained)   fenced      cannot corrupt your heap
libz                 TRUSTED     outside the guarantee — named, not hidden
The fence is a place, not a mode: your code's pointers never change meaning; the contained library's do, and its boundary is exactly the audited extern surface from Decision C. (All proposed.)
Ratified: "Own dial, decoupled from gc" — D-MEM-GUARANTEE1=A. contain: + harden: + jet inspect guarantees. implementation plan #1894.

# Distributed systems and consensus — domain census

## Verdict
Distributed practitioners choose Raft and FoundationDB when quorum safety, durable recovery, ordered state, and explicit failure behavior matter more than a thin API.
They choose Automerge and Yjs when local-first edits, deterministic merge, persistence providers, network adapters, and presence must work without hand-built conflict plumbing.
Jet already ships bounded CRDT values, deterministic merge, idempotent app.sync publication, typed protocol typestate, owned channels, bounded task groups, cancellation, and atomic Shared commits.
Jet is behind on production consensus, durable distributed storage, adapter-based sync persistence and transport, Jepsen/Maelstrom/VOPR-style fault campaigns, TLA+ interop, and the command surfaces that make those systems discoverable.

## Who does this work
The practitioner is a backend or infrastructure engineer who learned Go, C++, Rust, or Clojure and reaches first for etcd/raft, FoundationDB, a CRDT repository, and a failure harness.
They design replicated state machines, collaborative documents, storage layers, service protocols, or test models, then spend more time proving recovery and causality than writing the happy path.
The first success test is not “it compiled”; it is “two replicas converge or a failing schedule produces a replayable counterexample.”

## Core loops
### Raft / etcd-raft
1. Define a deterministic state machine and configure a Node with Storage.
2. Call n.Propose(ctx, data), deliver inbound messages with Node.Step(ctx, m), and advance logical time with Node.Tick().
3. Read Ready(), persist HardState/Entries/Snapshot, send Messages, apply CommittedEntries, then call Advance().
4. Observe leader terms, quorum commit, retries, membership changes, compaction, and linearizable or lease-read behavior.
### Automerge / Yjs
1. Create a document with Automerge.from or new Y.Doc() and obtain map/list/text shared types.
2. Apply a local change while online or offline; Automerge returns an immutable new value, while Yjs batches mutations in doc.transact.
3. Propagate change/update bytes through a chosen WebSocket, MessageChannel, BroadcastChannel, or persistence adapter.
4. Observe one converged document, history or update events, and optional Awareness presence without putting ephemeral state in durable history.
### FoundationDB
1. Open a cluster and use an ordered byte-string keyspace.
2. Run a transactional function that reads selectors/ranges and writes or clears keys; use subspaces/tuples/directories to avoid hand-built prefixes.
3. Commit with the database’s conflict/retry semantics and keep higher layers stateless over the same store.
4. Measure realistic parallel workloads separately from deterministic simulation and hardware-failure campaigns.
### Jepsen / Maelstrom
1. Start any-language nodes with JSON messages on stdin/stdout and diagnostics on stderr.
2. Choose a workload, node count, rate, concurrency, latency distribution, topology, and nemesis such as partition, kill, or pause.
3. Run the campaign, retain the complete history and schedule, and check it against a declared consistency model.
4. Open timelines, message statistics, time-series graphs, Lamport diagrams, and the minimal counterexample.
### TigerBeetle / VOPR
1. Submit batches of uniquely identified operations to a strict-serializable service.
2. Keep normal replication cost low with batching, pipelining, static allocation, and bounded leader work.
3. Run the actual cluster under deterministic network, storage, process, and gray-failure schedules.
4. Replay the failing schedule and verify checksums, recovery, upgrade state, and at-most-once processing.
### gRPC / Cap’n Proto / TLA+
1. Declare proto3 messages and services or Cap’n Proto interfaces and capability references.
2. Generate stubs/codecs or call promise-returning methods with pipelined dependent calls.
3. Model the protocol and invariants in TLA+ and check with TLC/TLAPS before trusting production schedules.
4. Keep schema, authority, deadlines, disconnects, and counterexamples visible in the same development loop.

## Performance
**Incumbent to beat:** FoundationDB distributed ordered key-value store.

**Workload and dataset:** official guide’s 90% read / 10% write transaction workload; 16-byte keys; 8–100-byte values; headline run on 24 EC2 c3.8xlarge machines, 16 cores each, 384 processes; separate latency run on 12 machines with 48 processes, E3-1240 CPUs, and SATA SSDs.

**Published numbers:** 8.2 million operations/second; under 75% load, transaction start 0.3–1 ms, read 0.1–1 ms, commit 1.5–2.5 ms; per-core reads about 55,000/sec on SSD and 90,000/sec in memory; writes about 20,000/sec on SSD and 35,000/sec in memory; peak throughput at about 200 concurrent operations. Source: https://apple.github.io/foundationdb/performance.html.

**Why it is fast:** ordered byte-string keys, short transactions, parallel processes over many machines, batching, and stateless layers over a replicated core; the guide publishes hardware, load, key/value sizes, and separate SSD/memory cells instead of one context-free number.

**Jet gauntlet coverage:** none; grep of gauntlet/matrix.json and gauntlet/measurement-manifest.json found no distributed, consensus, CRDT, FoundationDB, or TigerBeetle cell.

**What a Jet win must show:** the same ordered-KV 90/10 workload and key/value sizes with hardware/process identity, correctness, durability/recovery, p50/p95/p99 latency, throughput, RSS, and replayable fault schedules; CRDT merge and Maelstrom-style fault cells must be separate.

## Beat vectors
1. **B1 — shipped safety at local protocol and concurrency boundaries.** Jet’s typed protocol handles reject out-of-order transitions with E0150, channels move owned values, mutable captures and views do not cross, task groups bound admission, and cancellation/Shield preserve cleanup. Go/C++ consensus libraries leave much of this safety to callers; matching it would require changing their untyped or runtime-only boundaries. This is shipped in examples/features/concurrency/protocol.jet, docs/spec/architecture.md:169-190, and the Prelude sources.
2. **B2 — shipped CRDT merge plus integrated publication.** Jet’s core.sync has deterministic bounded text/map/list/counter merges and app.sync(doc, over: session) with idempotent generation publication, so the beginner does not first wire a CRDT to a push channel. Automerge/Yjs can copy the shape but their repository still requires storage/network adapters; Jet does not yet beat them on durable adapters, history, binary updates, or presence. Evidence: D-SYNC1, Sync.rs:16-21,2379-2481, probes/sync_min.out.
3. **B3 — ratified but unbuilt one evidence loop.** Jet’s proof/replay law binds target identity, hashes, effects, bounded records, and divergence diagnostics into versioned artifacts that could unify consensus schedules, consistency histories, and cluster replay. TLA+, Jepsen, and VOPR currently split modeling, checking, visualization, and replay across tools; Jet cannot claim the categorical win until jet prove produces and consumes the artifact. Evidence: docs/spec/proof-replay-decisions.md:1-25,66-78; feature-claims.json:1238-1266; probes/prove.out.

**What do we avoid:**
| Mistake in incumbent ecosystem | Evidence | Jet exposure |
| --- | --- | --- |
| Treating popularity or throughput as consistency proof | Jepsen defines consistency as a safety property over histories | Jet still lacks the history checker; its typed local boundaries do not prove distributed safety. |
| Last-write-wins overwriting concurrent offline edits | D-SYNC1 rejects the server-authoritative-only alternative for collaborative data | Basic CRDT merge is structurally covered; custom conflict rules and causal metadata remain gaps. |
| Mixing network/disk effects into a consensus core | etcd/raft’s deterministic Message/Ready seam leaves those concerns explicit | Jet has no equivalent consensus core yet; #Transact does not substitute for it. |
| Running fault tests without replay identity | FoundationDB Simulation and TigerBeetle VOPR make schedules repeatable | Generic replay is ratified but current producer probe fails E2105. |
| Unbounded task fan-out and accidental shared mutation | Jet group limits and crossing checks are compiler/runtime contracts | Keep these contracts when distributed service work lands. |
| Hiding remote authority in ambient names | Cap’n Proto makes capability references explicit | Jet local authority/effects do not yet carry remote capabilities. |
| Calling a single number a universal performance result | FoundationDB publishes workload, hardware, load, and concurrency context | Jet has no distributed gauntlet cell and must not invent a number. |

**Agent-optimality:** Verdict fidelity is high for Jet’s local ownership, typestate, cancellation, and CRDT malformed-state checks, but low for distributed quorum and recovery because those mechanisms are absent. Verdict latency is good for single-file protocol/CRDT checks but has no distributed campaign loop. Verdict actionability is strong in E0150’s named transition fix and weak where no consensus/fault command exists. Context economy improves when core.sync and app.sync replace hand-wired merge plumbing, but missing adapters force inference. Repair determinism is strong for deterministic merges and ratified artifact identity, yet the proof/replay producer must ship before agents can close distributed failures mechanically.

**Concrete surface coverage:** Covered with proof: SyncText, SyncMap<K,V>, SyncList<T>, SyncCounter, app.sync, protocol Payment, Payment.Client, channel<T>(), task.group, #Shield, #Transact, E0150, E1101/E1102, E3004, jet inspect live, jet debug, and the ratified jet prove --replay contract. Worth checking: SyncMap generic Codable values, map tie-breaks, replica overflow, durable live session recovery, jet debug --replay, jet perf, and #Replayable across tiers. Missing: Raft/Paxos/consensus APIs, durable ordered KV, StorageAdapter/NetworkAdapter equivalents, binary update protocol, Awareness, Jepsen/Maelstrom/VOPR harnesses, TLC/TLAPS interop, gRPC/proto3 codegen, Cap’n Proto promise/capability RPC, and distributed inspection commands.

## Avoid list
The source ecosystem’s strongest mistakes are making correctness depend on caller discipline, silently overwriting offline edits, treating a deterministic-looking throughput number as a safety result, and letting a fault campaign lose its schedule identity. Jet is structurally immune to accidental local view/capture races and out-of-order local protocol steps, but not to missing distributed mechanisms; absence must stay visible instead of being disguised by generic jet test or jet prove output.

# Foundations: transfer mechanisms, not feature lists

[Master report](index.md) · [Frontier research](02-frontier.md) · [Question map](coverage.json)

Jet should become easier to reason about by making fewer independent semantic promises, then making those promises stronger. That does not mean a small standard library or a narrow domain mission. It means one account of values, state, failure, time, ownership, and observations that survives every execution mode and tool.

This report answers questions 1–5. It combines historical lectures, creator retrospectives, current Jet law, and the collected implementation inventory. Historical claims are attributed to their authors. Design conclusions are this investigation's recommendations, not ratified changes.

## Context and evidence boundary

The corpus contains 18 factual packets and 2,717 records. Records include source metadata and gaps as well as claims. They are not 2,717 independent studies. The current-tree compiler build failed before this authorship pass. No recommendation below is evidence that Jet currently executes the proposed behavior.

The governing local sources are [the philosophy](../../spec/philosophy.md), [the living specification](../../spec/spec.md), [syntax decisions](../../spec/syntax-decisions.md), and [I1–I9](../../../AGENTS.md). Important existing laws include one semantic implementation, one compiler-held fact model, explicit expert control, memory safety by default, and identical meaning across execution modes. These laws already rule out much of the apparent feature shopping.

## Q1. Turing lectures argue for an intelligible system, not a bag of clever features

**Direct answer.** Take compositional specifications, small semantic foundations, checked transformations, visible execution, and experiments with explicit disproof conditions. Avoid treating fame, a compact notation, successful adoption, or a beautiful formalism as proof that a feature belongs in Jet. The lectures disagree about abstraction and implementation. Those disagreements are useful constraints, not a vote to count.

| Primary work and context | What the source contributes | Take for Jet | Avoid or retain as a limit |
|---|---|---|---|
| [Dijkstra, The Humble Programmer](https://www.cs.utexas.edu/~EWD/transcriptions/EWD03xx/EWD340.html), 1972 | Hardware growth enlarged the problems people attempted. Program structure and notation shape the programmer's reasoning. Proof and construction should grow together. | Define the proof obligation while defining a feature. Make an abstraction precise at its own level. Teach invariants and state changes, not punctuation alone. | His optimistic timetable did not establish a general bug-free method. Do not turn a program-size reduction or a short line into a comprehension claim. |
| [Hoare, The Emperor's Old Clothes](https://worrydream.com/refs/Hoare_1981_-_The_Emperors_Old_Clothes.pdf), 1980 lecture | His account connects successful language work to checking, fast feedback, clear specifications, and constrained scope. A failed large project lacked those controls. | Keep failure checks in the language contract. Demand an end-to-end executable slice before calling a subsystem complete. | Do not cite the story as proof that every large feature set fails. Jet's broad mission needs strong composition, not a smaller promised mission. |
| [Backus, Can Programming Be Liberated from the von Neumann Style?](https://doi.org/10.1145/359576.359579), 1977 lecture | Conventional state-oriented languages make algebraic composition difficult. Function-level combining forms provide laws for transformation and reasoning. | Carry purity, effects, and collection structure far enough to justify fusion and reordering. Publish the laws an optimizer uses. | FP's algebra is not a complete model of interactive, stateful, foreign, or concurrent Jet programs. Do not apply its equations to effectful callbacks. |
| [Milner, Elements of Interaction](https://archive.org/details/elements-of-interaction-turing-award-lecture-1ipyescuo1), 1991 lecture | Concurrency requires explicit interaction concepts. Sequential composition alone misses interference and causality. | Model tasks, channels, cancellation, and observations as first-class semantic obligations. | A final output does not describe event order, liveness, or intermediate state. An observational model can still omit causal information. |
| [Lamport, The Computer Science of Concurrency](https://lamport.azurewebsites.net/pubs/turing.pdf), 2013 lecture | State-machine reasoning separates an algorithm from its program representation and exposes safety and liveness requirements. | Specify lifecycle transitions and allowed histories before implementing resident sessions, tasks, or reload. | A state machine is not automatically small enough to explore exhaustively. State-space limits must be reported. |
| [Clarke, Emerson, and Sifakis, Model Checking](https://www-verimag.imag.fr/~sifakis/TuringAwardPaper-Apr14.pdf), 2007 lecture | Algorithmic exploration checks temporal properties and returns counterexamples. Abstraction controls state explosion. | Use small state models for stale results, cancellation, resource lifecycle, and reload transitions. Save the counterexample trace. | A bounded model is evidence about its model, not the whole implementation. Abstraction and environment assumptions need their own checks. |
| [Kay, Turing lecture](https://tinlizzie.org/IA/index.php/Alan_Kay_Turing_Award_Lecture_(2004)), 2003 award | The programming environment, language, and learning process belong together. | Design contextual explanation and manipulable examples as projections of the real compiler and runtime. | Do not require one visual environment or copy Smalltalk's complete object model. Portable CLI and editor paths remain first-class. |
| [Pearl, Mechanization of Causal Inference](https://ftp.cs.ucla.edu/pub/stat_ser/turing-award-lecture-ch2-acm-2021.pdf), 2011 award | Causal questions require assumptions beyond correlations in observations. | Keep “this change caused this improvement” separate from “these measurements moved together.” Name confounders in performance and learning studies. | The causal-inference machinery is not a reason to add AI or probabilistic behavior to Jet tools. |
| [Hennessy and Patterson, A New Golden Age for Computer Architecture](https://www.doc.ic.ac.uk/~wl/teachlocal/arch/papers/cacm19golden-age.pdf), 2017 award | Domain specialization and hardware/software co-design matter when general scaling no longer supplies easy gains. | Preserve domain facts through lowering. Compare the complete program on matched hardware and targets. | A specialized kernel win does not establish a general-language win. Keep portability and non-specialized paths in the comparison. |
| Wirth, language design and computer construction; [Modula/Oberon retrospective](https://people.inf.ethz.ch/wirth/Articles/Modula-Oberon-June.pdf) supplies a direct companion source | Language, compiler, representation, and machine were designed together. Formal syntax alone did not settle language quality. | Evaluate the complete toolchain, interface clarity, representation, and compile latency together. | Do not compare a compact closed system's line count with a multi-platform compiler as though scope were equal. |
| Cocke, performance in scientific processors; Hopcroft and Tarjan, algorithmic discipline | The collected lectures distinguish algorithm choice, compiler organization, and machine organization. Complexity analysis and experiments answer different questions. | Fix unintended copies and asymptotic work before tuning instructions. Record both scaling and matched measurements. | Do not infer asymptotic behavior from a single input or transplant a machine-specific result. |
| Gray, research goals; Reddy, possible dreams | The captured material emphasizes useful, testable goals and hypothesis-driven experiments. | Make a research proposal fail on a named counterexample or measurement. | Research optimism is not evidence that the proposal has worked. AI-specific product machinery is outside this task. |
| Ritchie, Wilkes, Floyd, Perlis, and Sutherland | Captured accounts discuss coherent interfaces, practical delays, programming methods, abstraction, and reconsideration of earlier designs. | Keep a method teachable, a tool usable, and a design revisable. A creator's later criticism matters alongside the original proposal. | Do not convert these diverse accounts into a single historical consensus. Some captures are scans, OCR, or retrospective material rather than an independently verified original lecture body. |

### The important disagreements

Dijkstra and Backus help Jet reduce unnecessary reasoning. They do not settle how stateful programs should be represented. Milner and Lamport require the missing interaction model. Kay and the learning literature then ask whether that model is visible to a person. Cocke and Hennessy/Patterson ask whether it survives contact with a machine efficiently.

The synthesis is a chain of obligations. A useful abstraction must have a defined meaning, a compositional implementation, an inspectable execution account, and a cost model. None substitutes for the others. Jet should reject a proposal that wins one link by hiding a loss in another.

### Lecture coverage is not complete

The ACM [lecture catalog](https://amturing.acm.org/lectures.cfm) and [winner list](https://amturing.acm.org/byyear.cfm) anchor the denominator. The collection did not obtain every lecture body. Classic gaps include Hamming, Minsky, Wilkinson, McCarthy, Knuth, Newell/Simon, Rabin/Scott, Iverson, Codd, Cook, Karp, and Pnueli. Several other records expose metadata, scans, incomplete text, or identity discrepancies rather than a clean primary body. Modern full bodies were concentrated in Kay, Lamport, Pearl, Hennessy/Patterson, model checking, and the joint deep-learning lecture. Missing bodies are not negative findings. Cyber-related material is excluded rather than interpreted.

No comparative claim in this report depends on counting those missing sources. The actionable lessons above stand on the named available material. A complete historical edition remains unestablished; it is not silently represented by the packet count.

## Q2. Language regrets show why the surrounding system matters

**Direct answer.** The recurring risk is committing to an abstraction without its operational, tooling, or compatibility consequences. Jet should copy complete mechanisms, keep prerelease correction freedom, and refuse to describe a static annotation as a runtime guarantee. The sources below are creator accounts, official rationales, and project surveys. They do not prove that the named design caused a language's overall success or failure.

| Language or family | Observed lesson and causal context | Jet consequence |
|---|---|---|
| [Rust roadmap](https://blog.rust-lang.org/inside-rust/2022/04/04/lang-roadmap-2024/) and [compiler survey](https://blog.rust-lang.org/2025/09/10/rust-compiler-performance-survey-2025-results/) | Ownership gives useful guarantees, but onboarding, compilation, IDE waiting, and tool contention remain real costs in respondent reports. | Preserve the guarantee while reducing repeated proof ceremony and exposing the reason for rejection. Measure cold and warm feedback separately. Survey responses are not Jet performance predictions. |
| [Zig release notes](https://ziglang.org/download/0.10.0/release-notes.html) and [async delay](https://ziglang.org/news/0.11.0-postponed-again/) | Self-hosting changed compiler capabilities and exposed immaturity. Foundational work forced an experimental feature out of a release. `ReleaseFast` and `ReleaseSmall` also change safety-check defaults. | Self-hosting is a product experiment, not proof of correctness. Never weaken Jet's safety or meaning by execution mode. |
| C [array-bounds proposal](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1990.htm) | Array-to-pointer conversion loses bounds information that later checks need. | Preserve length, ownership, and representation information at foreign boundaries. An annotation after information loss cannot recover the original guarantee. |
| C++ [creator interview](https://www.stroustrup.com/slashdot_interview.html) and [memory-safety proposal](https://isocpp.org/files/papers/P2771R1.html) | Compatibility, layout, ABI, and established code constrain change. Historical library omissions influenced design style. | Offer useful libraries and safe boundary types early. Improve C++ projects through bounded interoperation, not a promise to reinterpret arbitrary C++ safely. |
| [D origins](https://erdani.org/research/hopl.pdf) | Library fragmentation, incompatible language generations, and underestimated interoperation damaged a coherent adoption path. Some attractive features were later removed. | One canonical Core and one boundary contract matter more than isolated syntax. Jet is prerelease now; future external compatibility requires explicit contracts, not accidental promises today. |
| [Ada rationale](https://www.adaic.org/resources/add_content/standards/95rat/rat95html/rat95-p1-1.html) | Requirements, core language, specialized annexes, compilation units, and interfacing were considered together. | Use a common semantic core with domain libraries and explicit target promises. Breadth needs a support matrix rather than a universal badge. |
| [Pascal, Modula, Oberon](https://people.inf.ethz.ch/wirth/Articles/Modula-Oberon-June.pdf) | Module visibility and opaque representation aid separate reasoning. Unsafe type transfers, hidden global state, and lifecycle omissions erode it. | Keep module contracts precise and make representation escapes visible. Small implementation size does not excuse missing lifecycle behavior. |
| Java [erasure rationale](https://openjdk.org/projects/valhalla/design-notes/in-defense-of-erasure), [finalization removal](https://openjdk.org/jeps/421), [serialization redesign](https://openjdk.org/projects/amber/design-notes/towards-better-serialization) | Erasure served compatibility. Finalization and implicit representation-based serialization carried operational hazards. | Do not call a compromise irrational without its constraints. Prefer explicit resource lifetime and schema-controlled conversion over hidden finalizers or arbitrary object reconstruction. |
| C# [nullable references](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/nullable-reference-types) and [async return types](https://learn.microsoft.com/en-us/dotnet/csharp/asynchronous-programming/async-return-types) | Nullable annotations do not add runtime checks. `async void` and synchronous wrappers over asynchronous work have distinct error and scheduling consequences. | Separate checked facts from runtime values. Keep task result, cancellation, and failure ownership visible. |
| Go [error proposals](https://go.dev/blog/error-syntax) and [Experiment, Simplify, Ship](https://go.dev/blog/experiment) | Reducing repeated error syntax can hide control flow. | Python [PEP 484](https://peps.python.org/pep-0484/), [PEP 703](https://peps.python.org/pep-0703/), [packaging discussion](https://pyfound.blogspot.com/2023/02/python-packaging-strategy-discussion.html) | Optional static hints, interpreter execution, binary extensions, concurrency, and packaging have different contracts. Changing one affects the others. | A friendly core language needs equally coherent environment and foreign-library behavior. Do not advertise optional analysis as universal enforcement. |
| [JavaScript history](https://www.cs.tufts.edu/~nr/cs257/archive/brendan-eich/js-hopl.pdf) and [Node package exports](https://nodejs.org/api/packages.html) | Early coercion and representation choices became compatibility constraints. Stronger package encapsulation can break previously reachable entry points. | Prerelease is the time to remove false semantic equivalences. Later, preserve declared exports rather than every accidental internal path. |
| [Smalltalk history](https://worrydream.com/EarlyHistoryOfSmalltalk/) and [Lisp history](http://jmc.stanford.edu/articles/lisp/lisp.pdf) | A small compositional kernel can support a broad system. The first implementation and teaching model can also freeze accidental choices. | Retain composition and inspectability. Do not adopt macros, messages, or a universal object representation without their scope, tooling, and cost models. |
| [Standard ML history](https://smlfamily.github.io/history/SML-history.pdf) | A formal definition gave precision but still required correction and maintenance. | The specification itself needs counterexamples, executable interpretations, and review. | [Haskell history](https://simon.peytonjones.org/assets/pdfs/haskell-being-lazy-with-class.pdf) | Laziness and abstraction enabled composition while complicating space behavior, debugging, FFI, and library distribution. QuickCheck supplied a complementary method. | Keep property testing; make laziness and retention inspectable. Do not hide a materialization or unbounded retention cost behind a pleasant collection call. |
| [Julia's founding statement](https://julialang.org/blog/2012/02/why-we-created-julia/) | Combining desirable traits is a coherent ambition, but the initial system was not a completed proof of that ambition. | Jet can seek the strongest combination without claiming it has already won. |
| [Swift ABI stability](https://swift.org/blog/abi-stability-and-more/) | ABI, module, and source stability are distinct commitments. | Give each future external Jet contract an identity and boundary. Do not let a version string silently imply all forms of compatibility. |
| [Erlang thesis](https://www.erlang.org/download/armstrong_thesis_2003.pdf) | Isolation, messages, supervision, and recovery form a system. Operational reliability is not a theorem that application logic is correct. | Adopt structured task ownership and recovery as a package. A supervisor cannot repair an incorrect business rule or lost external effect. |

The practical disagreement is between early stability and early correction. Jet's owner has resolved the present case: Jet is pre-1.0, breaking changes are welcome, and present Jet-version migration machinery is not requested. That does not authorize deleting ratified history. It requires current documentation to distinguish a future policy from a shipped promise. [Release truth](07-readiness.md#release-truth) owns that correction.

## Q3. Cherry-pick only when the proof dependencies travel with the mechanism

**Direct answer.** Some mechanisms transfer cleanly as implementation or testing techniques. Others require a complete semantic bundle. The table is a transfer decision, not a list of dependencies approved for installation.

| Candidate | Required surrounding machinery | Failure if copied alone | Disposition |
|---|---|---|---|
| Algebraic collection rewrites | Purity/effect facts; alias and failure-order rules; integer and floating-point semantics; cost model | Reordered callbacks change observations; reassociated floats change answers; fusion retains data unexpectedly | Transfer the laws and their preconditions into shared lowering. Existing optimization and tier owners remain responsible. |
| Ownership or affine resources | Move/copy rules, aliasing, callbacks, destructor behavior, escape checks, diagnostics, foreign contracts | A “move” keyword can coexist with hidden aliases or duplicate a one-shot resource | Deepen the ratified value/borrow/fact model. Do not replace it with a paper's notation. |
| Effects and capabilities | Higher-order propagation, polymorphism, handlers, continuation multiplicity, scope and abstraction safety | A function appears pure while a captured callback or resumed continuation mutates state | Study the formal dependencies in [frontier research](02-frontier.md#q6). No new handler feature is authorized. |
| Typestate and session protocols | Ownership of state transitions, alias policy, cancellation, exceptional exits, protocol composition | One alias changes state while another retains an old permission; cancellation bypasses cleanup | Use existing facts where expressible. Research uncovered proof obligations under [#2925](index.md#card-2925). |
| Translation validation | A defined source/target relation, sound checker, full operation semantics, resource limits, certificate trust | “No counterexample found” is mislabeled as proof | Adopt as a proof technique only with explicit scope. See [compiler assurance](04-trust.md#q20). |
| Property and differential testing | Valid input generators, independent oracle, normalization rules, seeds, shrinking, result identities | All engines share the same wrong rule; generator exercises undefined behavior; normalization erases the defect | Reuse the existing hardening rig and strengthen its evidence rather than add a second runner. |
| Contextual teaching and execution views | Real source identity, compiler facts, runtime provenance, bounded capture, accessible fallback | A beautiful stale value teaches the wrong model | Reuse CLI/LSP/debugger paths. New assessment denominator belongs to [#2926](index.md#card-2926). |
| Foreign conversion | Source-language semantics, build inputs, libraries, ABI/layout, exceptions, callbacks, equivalence tests, manual remainder | Syntactically plausible Jet changes business behavior | Transfer in reviewable units. Preserve unconverted source as authoritative. See [interop](06-interop.md#foreign-conversion). |
| Incremental compilation | Complete dependency graph, negative lookups, environment identity, revision validation, deterministic invalidation | Fast stale answers replace slow correct answers | Reuse resident compiler and receipt law. A cache hit is a semantic claim, not merely a performance event. |
| Supervision and replay | Ownership, effect identities, cancellation policy, replayable inputs, external-operation rules | Restart duplicates a payment or replays an unavailable event | Keep explicit external boundaries. Local restart is not distributed exactly-once execution. |
| Self-hosting | Bootstrap chain, independent compiler comparison, reproducibility, build and debugging tools, stable enough core | One compiler reproduces its own bug and appears validated | Evaluate under the existing bootstrap gate. Do not make language choice itself a trust argument. |

The transfer test is counterfactual: remove the surrounding mechanism and ask whether the claimed benefit still holds. If not, the bundle is the candidate. Effort is not a reason to discard the better bundle. Unproved semantics, misleading guarantees, or an avoidable loss of control are reasons to redesign it.

## Q4. The missing silhouettes are relations between features

**Direct answer.** The evidence does not justify claiming that Jet lacks values, effects, tasks, proofs, a debugger, or interoperation. These are present in law or source. The weaker joins are between an intended rule and its executable, observable, current evidence.

| Predicted gap | Evidence-backed part | What remains a hypothesis | Consequence |
|---|---|---|---|
| Temporal validity of facts | Jet already records revisions, build identities, and replay provenance. The retained event model demonstrates how an old fact can attach to new source. | A complete census of every publisher and consumer has not been executed. | A fact needs an identity and validity interval, not just a value and source span. |
| Semantic coverage versus registry presence | Existing conformance and tier censuses explicitly distinguish registration from an observable result. Current build failure prevents fresh confirmation. | Exact present uncovered counts are unavailable. | Completion must be a relation over behavior and applicable execution modes. |
| Teaching the behavior between input and output | CLI/LSP/debugger source exists; learning research shows that producing code and predicting it are distinct skills. | Jet-wide human learning gains are unmeasured. | Teach transitions and counterexamples, not only syntax help. |
| Foreign lifecycle and causality | Binders and bridge provenance preserve parts of a boundary; foreign callbacks, destruction, and errors need contracts. | Near-native performance and complete language conversion are unproved. | Keep lost information visible at the boundary. |
| Optimization as an accountable decision | Ratified acceleration and inspection work already exists; historical probes found copies and order-sensitive results. | Full current decision coverage and performance are unmeasured. | Explain which facts licensed a transformation and how to reject it. |
| Current release truth | Maintained versioning text conflicts with the owner-confirmed prerelease state. Ada/Pascal command acceptance and the binder-only map are consistent; neither implies semantic conversion. | A full claim census remains to be run. | Correct the confirmed release wording, and classify command acceptance separately from conversion capability. Preserve historical policy. |

These are hypotheses about missing relations, not invitations to create six new subsystems. The strongest move is to connect the existing compiler facts, diagnostics, result records, examples, and release denominator.

## Q5. First principles lead to a behavior contract, not more syntax

**Direct answer.** A program transforms values while interacting with an environment. To reason about that transformation, a person must know what may change, when it may change, who owns the change, what may fail, and what evidence supports the answer. Derive new work from those needs before proposing a keyword.

1. **Values need meaning.** Types, numeric rules, equality, representation, and conversion define the result. Existing types and facts already cover much of this need.
2. **Changes need ownership and order.** Borrowing, effects, task structure, lifecycle, and event histories define who can change state and when. Temporal identity is the overlooked cross-cutting obligation.
3. **Abstraction needs a preserved contract.** A function, module, optimizer, foreign bridge, or editor projection must not silently invent a different meaning. Existing I3, I8, and I9 provide the law.
4. **Knowledge needs provenance.** “Proved,” “observed,” “inferred,” and “unknown” are different answers. A result must name its program revision, assumptions, and relevant environment.
5. **Work needs useful defaults and an inspectable override.** Frequent operations should not require a setup ritual. Experts must be able to reject an optimization, control resources, and inspect the decision.
6. **Learning needs a testable mental model.** A user should be able to predict a small change and explain an observed result. The compiler's account should remain available outside a visual studio.

The proposed unifying object is a **behavior contract**: the existing semantic facts plus their scope, observations, and proof obligations. This is an architectural description, not a new Jet type or public API. It must reuse the ratified fact law and ledger. If implementation discovers a genuinely new public type or protocol, that choice needs its own ballot.

A counterexample keeps this idea honest. A `Float` calculation can be well typed, memory safe, and executed identically by every engine while still applying the wrong tax formula. No compiler can infer an unstated business rule. Domain contracts and human review remain necessary. A behavior contract makes that missing premise visible; it does not invent intent.

## Competitive and agent-development consequences

Jet's possible advantage is the complete loop: ask what a program means, inspect why, change it, rerun the same command, and get a smaller or empty error set. Existing `jet check`, `jet fix`, `jet explain`, `jet inspect`, `jet dev`, and structured results are the concrete carriers. This is not yet a measured win.

Measure verdict fidelity, feedback latency, actionability, context required, and deterministic repair separately. A fast false-green result loses. A repair that changes intent without permission loses. The same rules help human and agent authors; no AI dependency is needed in Jet itself. Exact comparator and per-domain obligations appear in [the frontier report](02-frontier.md#q8).

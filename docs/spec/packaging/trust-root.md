# Trust-root publication

This page defines the public keys that anchor signed Jet index, cache, and
toolchain metadata. The publication tree is generated by
[`jetpack-trust-root`](../../../crates/jetpack/src/bin/jetpack-trust-root.rs)
and staged by
[`stage-trust-root.sh`](../../../tools/jetpack-infra/stage-trust-root.sh).
The checked-in manifest and operator-facing copy are in
[`site/dist/keys`](../../../site/dist/keys/). The tree contains public key
files and `trust-manifest.json`; it never contains an HMAC `TrustKey` secret or
a signing seed.

## Public-key contract

The manifest uses schema `1`. Each key record names its role, algorithm, key
id, exact client path, and padded base64 public key. Client trust files use one
line in the strict `key-id:base64-public-key` format:

```text
keys.jet-lang.dev/nix-index-v1.ed25519.pub
keys.jet-lang.dev/nix-cache-v1.ed25519.pub
keys.jet-lang.dev/toolchain-v1.ed25519.pub
```

The three role files contain Ed25519 public keys. The index file is consumed by
the signed `NixIndex` verifier. The cache and toolchain verifiers use the same
strict public-key format. The Hangar cache writer's HMAC role key remains a
private host binding and is never exported.

The stable index key document is the single-line file at
`https://keys.jet-lang.dev/nix-index-v1.ed25519.pub`. When a key is prepared,
`trust-manifest.json` records its key id and `ed25519` algorithm. The signed
index manifest supplies its validity window through `issued_unix` and
`expires_unix`. The raw key remains in the exact shape consumed by the client,
so publication does not create a second key parser or trust mechanism.

The checked-in `trust-manifest.json` is deliberately marked
`awaiting-key-ceremony` with an empty key list. It does not use
`repo-dogfood-index-v1` or `jet-test-index-v1` as an official root. Test and
dogfood keys are rejected by the exporter rather than copied into the owned
domain as stand-ins.

## Pin keys on the client

The signed-index client reads the pinned key from:

```text
<JETPACK_ROOT>/trust/nix-index-v1.ed25519.pub
```

Its reviewed endpoint setting is:

```text
<JETPACK_ROOT>/config/nix-index-v1.endpoint
```

For the official tier, that file contains `https://index.jet-lang.dev`. Install
it together with the pinned key. There is no implicit official endpoint while
the trust configuration is absent.

The client never fetches a key and then trusts it. A host-returned key is only
an update candidate for a separately reviewed manual update. The client checks
the configured key id, algorithm, and public bytes against each manifest and
index signature; a substituted key is refused as E1348.

## Prepare public files

The exporter accepts only public key files. Provide files from the offline key
ceremony, then run:

```sh
tools/jetpack-infra/stage-trust-root.sh \
  --index-key <public-index-key> \
  --cache-key <public-cache-key> \
  --toolchain-key <public-toolchain-key> \
  --bootstrap <jetpack-root>
```

The exporter accepts a regular file containing one padded
`key-id:base64-public-key` value whose decoded Ed25519 key is exactly 32 bytes.
It rejects test key ids, symlinked inputs, private material, and changed bytes
at an existing immutable publication path. The wrapper never creates or reads
a private key.

Rotation is an offline threshold-root operation:

1. Generate the replacement key outside this repository and give it a new key
   id. Keep the old key and retirement time in the operator log.
2. Have the old threshold root verify the replacement root metadata. Update
   the local bootstrap pin and prepare the replacement public files.
3. Publish replacement key files and signed catalog metadata together as
   immutable static files. Do not overwrite an immutable target with different
   bytes.
4. Make a reviewed manual update of every verifier's local trust file. A
   verifier learns that the old key is retired through that reviewed update;
   it never switches keys because a host returned different bytes.
5. Let the old signed catalog's `expires_unix` pass, then remove the old key
   from the reviewed publication set. A verifier with the old pin fails closed
   until its manual update.

This procedure does not generate production key material or perform the key
ceremony. It records the trust boundary that the ceremony and its reviewer
must satisfy.

## Publish a static root

After the signer, DNS, TLS, hosting, and owner acceptance gates are satisfied,
copy the immutable publication tree into the host root:

```sh
rsync -a --checksum --ignore-existing site/dist/keys/ "$HOST_ROOT/keys/"
```

`HOST_ROOT`, DNS, TLS, production signer custody, and publication approval are
external to this repository. The command writes a local host root; it does not
publish to the internet by itself.

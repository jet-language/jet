Jet for every kind of work

Jet's foundations are strong everywhere, but the layer that lets a person do real work in a specific field is missing and unmeasured; this plan builds that layer once, as shared parts, and proves each field with a benchmark before calling it done.

Shipped Foundations

Safe typed data, exact numbers, receipts on every result, What/Why/Fix errors, one meaning on every execution tier.

Shipped Developer experience

Devtools, one live loop, entry resolution, the web suite, jobs.

Now The survey

108 fields of work measured against the best tool in each.

Proposed Shared parts

Build the building blocks the fields have in common, widest first.

Proposed Proof

A field counts as done only when stock Jet beats its incumbent on a fixed workload.

Where we are

The survey said the same three things everywhere

We asked one question for 108 fields of work, from web servers to acoustics to double-entry accounting: what does the best tool in that field let a person do in the first five minutes, and can stock Jet do the same? A "field" here is a kind of work, not a company; the best tool is whatever practitioners actually reach for, such as MATLAB for signals or Excel for a budget. The answers came back in the same shape every time.

The foundations hold

In every field, the parts Jet already has are graded strong: data that is typed and bounded, numbers that are exact, results that carry a receipt, and errors that say what happened, why, and how to fix it. Example: opening a CSV in Jet gives a typed table with a row limit and a receipt; a bad column produces a What/Why/Fix error instead of a silent guess.

The field layer is missing

On top of the foundations, each field needs its own value types, its own engines, its file formats, and a first-five-minutes loop of open → do → see. Almost none of that exists yet. Example: an audio engineer in MATLAB has a signal type, filter design, and a spectrogram in one line each. Jet today has one FFT, implemented as a slow reference, and no way to design a filter.

Nothing is measured

96 of the 108 fields have no benchmark against their incumbent at all. The other 12 borrow a generic one that does not measure the field's real workload. So no field can claim a win yet, in either direction.

More precisely The survey also found a short list of foundation bugs that block claims Jet already makes, for example the default evaluator rejecting lazy data paths in six fields. They are fixed first, before any field work.

Where we could be

Not 108 products. One foundation, about 120 shared parts

The fields overlap far more than they differ. A "part" is one building block many fields need: an FFT family, a table type, a ledger, a scene graph, a units system. After merging duplicates, the 108 fields share about 120 parts; 51 of them serve five or more fields, and the widest dozen serve between 26 and 59 fields each. Build the widest parts first and each one unlocks many fields at once. Each field then needs only its own vocabulary on top, one example program, and its benchmark.

After

fn run() {
    recording :: signal.read_wav("Turbine48k8192.wav", channel: 0, rate: 48_000.0) ?? panic("wav")
    first :: signal.spectrogram(recording, frame: 4096, hop: 2048, window: .Hann, provider: .Auto) ?? panic("spectrum")
    filter :: signal.butter(recording, order: 6, cutoff: 8_000.0, phase: .Zero, mode: .Offline) ?? panic("filter")
    filtered :: filter.apply(recording) ?? panic("apply")
    reduced :: signal.resample(filtered, rate: 12_000.0, anti_alias: .Required, provider: .Auto) ?? panic("resample")
    print("spectrogram_shape:{first.frames}x{first.bins}")
    print("batch_receipt:{first.receipt.id}")
}

One shared FFT part serves signal processing, acoustics, and radio at once; the receipt names which engine produced the result and at what precision.

What Jet can offer that the incumbents cannot

Every result in Jet arrives with a receipt: where the data came from, which engine computed it, at what precision, on which machine, and how to replay it. The incumbents cannot offer this because their instrumentation is bolted on afterwards; Jet's is built in. A field is won when the incumbent's five-minute loop runs in stock Jet with that receipt attached, and the benchmark shows Jet ahead.

Where the parts live

Each part has one meaning, defined in Jet's standard library: its types, its operations, a reference implementation, its errors, and its receipt. Faster engines, such as FFTW for the FFT or a GPU for a matrix, plug in behind that same meaning and the receipt says which one ran. A single-file program gets the part without a manifest; an expert can pin an engine, forbid one, or work offline.

The proof rule

Every field gets a benchmark: a fixed workload, the incumbent it is measured against, and the numbers that count. The benchmark runs when the field's work starts. A field cannot be called done while its benchmark is missing or losing, and a loss is never averaged away by a win elsewhere.

What day one looks like

One flagship field per family opens first, so there is something real to use early: numerical computing, signal processing, genomics, mapping, quantitative trading, machine-learning training, image processing, embedded devices, databases, cryptography, and test automation. Any flagship can be swapped before it opens.

What has to be decided

Three questions gate everything else

Where do field features live?

In the standard library, in separate packages, or meaning in the library with engines in packages. The answer sets whether every field shares one meaning per part, what a single file can use without a manifest, and how fast new fields can ship.

When is performance measured, and can a field close without it?

Measure everything up front, measure only flagships, or register every benchmark now and run each when its field starts. The answer trades honesty about wins against how much work can move at once.

What gets built first?

Family by family, widest parts first, or widest parts first with a small number of flagships open in parallel. The answer decides whether the first usable result arrives early or after the shared parts are complete.

Behind these three sit 42 part-level design questions, one per shared part, each with the same shape: what does the person type, and which engine runs it. All of them are open on the board with a recommendation each; this page is the context, the board is where they are decided.

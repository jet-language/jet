Most build-time work is a normal function

Packing sprites, parsing SQL, baking a table — those are functions you write and call. Reading the disk and the network should be the same effect system as runtime. b is only the order form you hand the compiler.

IO = functions + effects + lock b is the plan Call their helper, or include their sandboxed build

The point

You already have compile-time function calls. This is a real example in the repo:

fn make_table() -> [Int] {
    t := [Int]{}
    loop i in 0..9 -> t.push(i * i % 7)
    t
}

@table :: make_table()   // runs while compiling
                         // the finished program just has the numbers

No BuildContext. No b.action. A function returns a value. The @ means “run this while compiling, store the result.”

That is the default. Use it whenever the answer is data (a table, bytes, a string of source text you computed).

Three different jobs

The last pages mixed these together, so everything looked like it needed b.

JobWhat you wantTool
1. Compute Turn inputs into a value: an atlas, a table, Jet source as text A normal function. Call it. Do not put this logic in fn build.
2. Borrow the machine Read the project’s PNG folder, fetch a pinned URL, run an outside program The effect row says this function may do FS/Net/Exec. Package policy can still say no. The lockfile records the exact files and hashes. Pass the bytes into job 1.
3. Tell the compiler what to compile “The game binary is src/game.jet plus this generated file” Write that on a plan and return the plan. fn build exists for this.

fn build is the compile-time main. Same idea as runtime fn run: one entry the tool looks for. It should be a short script — get inputs, call helpers, fill in the plan, return.

What b (BuildContext) is

Today’s law treats b as two jobs glued together: a key to the machine, and an order pad. That glue is the duplicate you spotted. Keep the pad. Drop the key.

  1. Order pad — keep. b.add_executable, b.generate, b.plan do not “do the compile.” They write a line on the pad. After fn build returns, a separate driver follows the list. A string in memory vanishes unless the plan says “this is source, compile it.”
  2. Key — this is the effect system. b.find / b.fetch / b.embed are a second spelling of FS and Net. See Effects vs b.

Kitchen picture — and where it stops

A helper is a recipe. Effects are the health-and-safety rules: this cook may use the oven, this one may not. The lockfile is the receipt: these exact ingredients, this hash. b is only the ticket you hand the pass: “serve this binary, include this generated file.”

The picture stops here: the compiler is not a waiter. It reads the ticket after fn build returns. That is why a plan exists at all.

What a BuildPlan is

A plan is the filled-in ticket: the list of programs to build, the source files each one uses, the generated files to include, the outside steps that must finish first.

fn build does not compile your game. It returns the list. The compiler then follows the list. That is why the function is typed as “takes a context, returns a plan.”

If you only need a baked table in one file, you never write fn build. The default pipeline already knows how to compile a package. fn build is what you add when the default list is not enough: extra generated modules, extra binaries, extra tools.

Why b.action exists — and when it should not

A function call runs now, in Jet, and gives you a value. Then it is done.

b.action is for a different sentence: “there is a program that is not Jet (bindgen, an atlas packer you already ship, clang). Run it only when these files changed. Here are its inputs, its outputs, and the permission it needs.” That is a cacheable graph node, the same idea as Make. The driver, not your function, decides whether it is stale.

Wrong picture (last page)

fn build(b: BuildContext) -[FS, Exec]> BuildPlan {
    atlas :: b.action("pack-sprites",
        inputs: b.find("assets/sprites/*.png"),
        outputs: ["build/sprites.atlas"],
        run: ["atlas-pack", "…"])
    b.generate("sprite_ids") { /* logic here */ }
    …
}

This made packing look like a special build verb. It isn’t, if packing is Jet code.

The picture you asked for

fn pack_sprites(pngs: [Bytes]) -> Atlas {
    // ordinary Jet. Call this at build
    // time or, later, at runtime.
}

fn sprite_ids_source(atlas: Atlas) -> String {
    // ordinary Jet. Returns text that
    // happens to be Jet source.
}

fn build(b: BuildContext) -[FS]> BuildPlan {
    pngs :: find("assets/sprites/*.png")
    atlas :: pack_sprites(pngs)
    b.generate("sprite_ids", sprite_ids_source(atlas))
    game :: b.add_executable("game",
        sources: ["src/game.jet"],
        generated: ["sprite_ids"])
    return b.plan(game)
}

Use b.action only when the worker is another executable. If the worker is Jet, it is a function.

Today’s shipped spelling of generate is a block of typed items, not generate(name, string). The idea is the same: compute the contents in a helper, then register them. The register step needs b because a string sitting in memory vanishes when fn build returns, unless the plan says “this is source, compile it.”

Effects vs b.find — you are right, it is a duplicate

Jet already has one rule for “may this function touch the world?”:

fn build(b: BuildContext) -[FS, Net]> BuildPlan { ... }

fn secret() -[!Net]> { ... }     // cannot fetch, even if a caller could
# package policy can also deny Net for the whole project

Then today’s build API asks you to say it again: b.fetch(...), and sometimes a third time as caps on b.action(..., ["FS", "Net"]), and a fourth as #Impure("reason").

That is the same door with extra locks that do not add a new fact. -[Net]> already means a network call is legal. -[!Net]> or a package deny already means it is not.

What effects cannot do, and must not be lost:

JobWho does itWhy it is not an effect
May this function use the network at all? Effect row + package policy This is the effect system. Do not copy it onto b.
Which bytes went into this binary, so CI can replay it? Lockfile: path or URL + hash Effects say “Net happened.” They do not say “these 214 lines of gl.jet.”
Which programs to compile? The plan on b Not IO. Not an effect.

So: find, embed_file, and fetch(url, sha256:) should be ordinary functions. While compiling, the interpreter already has to intercept IO. Let it check the effect row, then write the hash into the lock. You do not need b.fetch for that.

fn build(b: BuildContext) -[FS, Net]> BuildPlan {
    sql  :: find("schema/*.sql")                 // FS. lock records the files
    spec :: fetch("https://…/gl.xml", sha256: "…")  // Net. lock records the hash
    b.generate("db_client", sqlx.client_source(sql))
    return b.plan(b.add_executable("api",
        sources: ["src/run.jet"],
        generated: ["db_client"]))
}

If someone writes fn build(...) -[!Net]>, fetch is a type error. Same as runtime. Unpinned http.get at compile time stays behind #Impure — that gate is for “the bytes can change,” not for hashed fetch.

Recommended split

One IO system: functions + effects + lock. b shrinks to the plan: add_executable, generate, merge a package fragment, and action only for outside programs.

Calling a package’s build from yours

Today a dependency’s fn build is checked and never run. That is why an SQL crate cannot type your queries unless you copy its generator. Your idea — an explicit call in your fn build — is the right audit shape. Import must not start work. A line you wrote must.

Do not pass your b into the crate. That is the Cargo build.rs hole with a function call on top: one extra line to read, and they still inherit your disk and your network.

Two kinds of package, two calls:

1. They transform your files

SQL, SOA, id enums. They never need a key. They are a function. You read, you call, you put the result on the plan.

fn build(b: BuildContext) -[FS]> BuildPlan {
    sql :: find("schema/*.sql")
    b.generate("db_client",
        sqlx.client_source(sql))
    return b.plan(...)
}

2. They ship their artifacts

OpenGL bindings from their pinned spec. A native lib they compile. You opt in with a call. Their code runs with their rights: their files, their hashed URLs, not your $HOME.

fn build(b: BuildContext) -[FS]> BuildPlan {
    gl :: b.use(opengl)   // their sandboxed build
                          // merged into your plan
    game :: b.add_executable("game",
        sources: ["src/game.jet"],
        generated: gl)
    return b.plan(game)
}

You still audit one file. The crate still defines the steps you would have copied. The effect row on your fn build only needs the IO you do. Their fetch is on their fragment, under their lock entries.

Worse shapes, for the same product:

ShapeWhat goes wrong
Import runs their buildJai. No line to grep. A crate you typed in a use-list phones home.
pkg.build(b) with your contextYou can see the call. They can see your machine.
A manifest enable: list and no callAuditable, but now you have two places that mean “this build uses sqlx,” and helpers still need a call for your paths.

Sprite atlas — written as functions

You want a game whose PNG folder becomes one atlas, plus names like HeroIdle you can use in code.

fn pack_sprites(pngs: [NamedBytes]) -> Atlas {
    // walk rectangles, blit, return { image, names }
}

fn ids_module(atlas: Atlas) -> String {
    // "enum Sprite { HeroIdle, … }"
}

fn build(b: BuildContext) -[FS]> BuildPlan {
    pngs  :: find("assets/sprites/*.png")
    atlas :: pack_sprites(pngs)
    b.generate("sprite_ids", ids_module(atlas))
    @atlas_png :: atlas.image              // bytes into the binary
    return b.plan(b.add_executable("game",
        sources: ["src/game.jet"],
        generated: ["sprite_ids"]))
}

What actually needed b: saving generated source onto the plan, and naming the executable. Listing the folder is find (an effect). Packing is a function.

If packing is an old C++ tool you still run: that one line is b.action, because the worker is not a Jet function. Then a Jet function can still read the tool’s output and build the id module.

Typed SQL client — written as functions

You want get_user(id) to exist, with a UserRow that matches the SQL, and a compile error if a column is renamed.

fn client_source(sql_files: [String]) -> String {
    // parse CREATE TABLE / SELECT, return Jet source
}

fn build(b: BuildContext) -[FS]> BuildPlan {
    sql :: find("schema/*.sql")
    b.generate("db_client", sqlx.client_source(sql))
    return b.plan(b.add_executable("api",

fn handler(id: Int) -[IO]> UserRow {
    db_client.get_user(id)
}

The parser is a function in the sqlx package. You can unit-test it. Importing sqlx does nothing. The call is the hook.

Sin table — no fn build at all

fn sin_table() -> [Float] { … }

@sins :: sin_table()

fn run() {
    print(@sins[3])
}

If the result is a value in the binary, stop here. No plan. No b.

What you still cannot ship, even with this picture

ProductWith this modelStill missing
Atlas, SQL client, C bindings, org “every Entity has archive” Yes, in your app, as functions plus a short fn build Some of this is law ahead of the compiler.
Install a crate and get its generator without copy-paste Not on import. Yes if your fn build calls their helper or includes their sandboxed build. Auto-run on import is refused.
Packet[N] No. A known constant can size an array. A number as a type parameter cannot yet. Const generics later. Not types-as-values.
A type that exists only inside one call, no file No Do not add splice.

Settled this round

Compile-time find / embed_file / fetch(url, sha256:) are ordinary functions. Effects and package policy allow or deny them. The lockfile records hashes. b is the compile plan.

A package participates when you call it. Helpers get data you pass. Their own fn build runs in their sandbox when you include it. They do not get your b. Import does nothing.

Does not reopen syntax law, create a Tower card, or implement anything. Examples use one arrow, type after it, body in braces.

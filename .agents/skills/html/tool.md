# HTML tool branch

Read this file only when the user explicitly requests an interactive page, editor, prototype, gallery, dashboard, or another tool surface.

A tool has its own shape and skips the report branch's status/proposal acts, story gate, and report density rules. It still uses the canonical visual identity, resolved design plan, exact target scope, and implementation handoff.

## Tool route

1. Name the subject, audience, and one job of the page.
2. Identify the characteristic screen, diff, trace, or interaction the reader must see first.
3. Resolve the state model, controls, empty and error states, keyboard behavior, and responsive behavior before delegation.
4. Choose the closest asset for mechanics. If no asset matches, combine the two closest patterns without changing the identity.
5. Pass real content and data to the implementation worker. Do not use sample data when real data exists.

Prefer HTML when the requested result needs multi-column or side-by-side comparison, interactive controls, color-coded states, charts, diagrams, flowcharts, slides, inline code review, or more than about 500 words that need visual hierarchy. Keep a small result in its native format when the user did not ask for HTML.

A tool is complete only when the declared interactions work in the real browser at the required widths, controls are keyboard-operable, errors and empty states say what happened and what to do next, and the orchestrator has checked the console. The implementation reference defines the worker brief and browser closeout.

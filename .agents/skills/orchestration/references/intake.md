# Submission intake and batch integration

Workers write code and submit it. The orchestrator builds, tests and lands it.
A worker never commits, builds the compiler, or runs a suite, census, chain or
release.

## What a worker runs

`jet check` of the files it touched and a single-file `jet run` or `jet test`
of a test it wrote, one at a time, under `nice`, with the admitted seed or the
batch compiler the orchestrator last announced. Anything that needs a freshly
built compiler goes in the submission's `tests`.

The worker never builds the compiler and never runs the submission gate,
suites, censuses or chains. It submits and moves straight on to its next task.
At intake the orchestrator runs a quick, narrow, targeted check on each
submission: the lander's submission gate on the patch applied to the current
train's composed tree, with that train's already-built compiler. The gate runs
the guards, the Core coverage ratchet, the formatter pins, every generator's
`--check` and every `Jetpack/Bootstrap/Check.jet --area` in keep-going
mode. Every finding goes back to the worker as one list, and the worker fixes
the whole list in one pass alongside its new work. Only a submission with a
clean gate enters a train.

A change that makes sema, a guard or a gate stricter names the rule's reach in
its `msg`. The gate sweeps it against every Jet source it can reach (Core,
Compiler, Jetpack, Tools, Examples, every `tests/` tree, case fixture and
template), and every hit is fixed in one pass.

## The submission

One folder per submission in the orchestrator's inbox
(`$JET_SCRATCH_ROOT/lanes/<orchestrator>/inbox/<Worker>-<n>/`), never reused:

- `patch`: `git diff --binary --full-index` against a recent `dev`. The worker
  makes it with `git -C <its export> diff`, never by committing, and never with
  `GIT_DIR`, `GIT_INDEX_FILE` or `GIT_WORK_TREE` exported.
- `msg`: the commit message: what, why, evidence, disclosures.
- `tests`: one command per line, run from the tree root, with `jet` meaning
  the batch compiler. Name the narrowest proof.
- `cards`: one `#card cN claim` line per criterion claimed.
- `meta`: `base: <sha>`, `stack: <earlier submissions it needs, or none>`,
  `seed: none` or `seed: <what the seed must carry>`.

A patch that adds Prelude or registry rows (a dispatcher row, a fixed
signature, a new reserved member, a runtime export) and also uses them from
Core cannot pass the census, because the census checks Core with the admitted
seed. Split it: part a adds the rows, runtime and tables with no Core use;
part b uses them, says `seed: <part a>`, and lands on the first seed that
carries part a.

Generated files (a `generated by Tools/…; do not edit` header) may be left out:
integration always discards their hunks and reruns their generators. A worker
that moves a line of a Core file regenerates every golden citing
`<corelib>/<that file>:LINE`.

## A batch

Batches run as a rolling train, and trains overlap: the next train's census
starts on the current train's composed tree while the current train tests, so
it launches already clean when the current train lands. Trains run
continuously. When a train's preflight or census finds failures, every
failure is collected in one pass and goes to its owner as one list. After the
fixes, the train retests only the affected rows and continues. It never
restarts to find the next failure. A train leaves about every 45 minutes, or
sooner when a heavy slot is free, with every ready submission that is not
waiting on a seed, in stack order. It lands whatever passed. One failing
submission is set aside and the rest land in the same cycle; a train is never
rebuilt from the start for one submission. A submission whose patch changes no
build input of the compiler, the runtime or Core is tested with the last
train's compiler and lands without a census. The orchestrator may hand the
train to the Lander it names (AGENTS.md, Delegation):

1. Export `dev` and apply each submission with a three-way merge, excluding
   generated files. A conflict inside a generated region keeps the base side
   and is regenerated; a conflict in a `.tsv` row table keeps both sides' rows.
   Any other conflict, or a failed stack dependency, sets the submission aside.
2. Rerun every generator the batch touched, on the composed tree.
3. One collect-all census: check, build, guards, runtime pack, self-check,
   Core self-check. Then the repository ratchets, every submission's `tests`
   with the built compiler, and every golden that cites a touched Core or
   Prelude line.
4. If the census fails, set aside every submission its rows name, with that
   worker's later submissions, and rerun the rest in the same cycle.
5. Send each author every failure attributed to it, in one message. Announce
   the batch compiler's path for workers' checks.
6. Land each passing submission on `dev` as its own commit (its rebased patch,
   with a `Lane:` trailer), then one commit with the regenerated tables. Refuse
   to land if `dev` moved in build inputs since the batch's base. Meet each
   `cards` claim on Tower with the batch as evidence, then delete the landed
   inbox folders.

Part b submissions join the first batch after a seed carrying their part a is
published.

A train that changes the version, the engine protocol or a C dependency makes
the admitted seed's `jetpack` disagree with the batch compiler. The batch then
tests with the `jetpack` its own census built, placed beside the batch
compiler, never with the seed's.

## Train speed

A train's cost is its repeats, not its stages. One build and census take about
20 minutes, but t22 (2026-11-11) took more than two hours across seven census
runs and one 39-minute full test pass. These rules bind every train:

1. **Gate before the build.** After composing, run a keep-going `jet check`
   with the admitted seed on every package a submission touches. A row that is
   new in a touched file sets that submission (and its stack) aside before the
   build. Rows already red on the base, and rows a `seed:`-split part b
   expects, don't count.
2. **One build per train.** A failure after the build never restarts the
   train. Set the failing submission aside and land the rest on the same build.
   Rebuild only when a set-aside submission changed compiler, runtime or Core
   build inputs, and then only once for all of them.
3. **Affected rows only, sharded.** Each submission's own `tests` lines run
   first. Then the rows its paths reach: a `Compiler/` submission reaches the
   ui and golden profiles, and any other package reaches its own tests. Run
   them in parallel shards sized to MemAvailable minus 12 GiB, with each jet
   capped at 16 GiB. Full suites belong to milestones. The test stage aims at
   under ten minutes.
4. **Fail fast.** The moment one of a submission's rows is red, mark it set
   aside and keep testing the others. Triage never waits for the whole pass.
5. **Independent trains.** Compose the next train on `dev` plus its own
   submissions whenever its paths are disjoint from the current train's, and
   gate it while the current train builds and tests. Rebase only overlapping
   submissions, after the current train lands.
6. **Small trains.** About eight submissions, grouped so one owner's stack
   can't hold the others.
7. **A sealed tree.** The composed tree lives in a sealed subdirectory that is
   read-only for the length of the run. Nobody but the lander writes, moves or
   deletes anything under the train directory, and nobody copies from it:
   workers compose their own trees from git objects or a published seed.
   Area checks and tests run with an empty scratch directory as their working
   directory, never the tree.
8. **Timings in every report.** Each train `REPORT.md` has a stage table
   (compose, gate, build, census, tests, regen, land) with wall minutes, and
   every restart names its cause.
9. **Two trains in flight.** While MemAvailable stays above 12 GiB, the next
   train composes, gates and builds alongside the current one, on disjoint
   paths. Cut trains back to back, so the build slot is never empty while the
   inbox holds ready submissions.
10. **Direct lands.** A submission that changes no build input of the
    compiler, the runtime or Core is tested with the last train's compiler and
    lands on `dev` at once as its own commit, without joining a train. Sweep
    the inbox for such submissions at every landing.
11. **Release every train.** After a train that changes a compiler, runtime
    or Core build input lands, `jet run Tools/release/Main.jet -- admit
    COMMIT` runs on that commit in the next free build slot, alternating with
    trains. Admit writes the owner's current release, so the owner's `jet`
    stays at most one train behind `dev`. A failed admit reports every lost
    row in one pass, routes each root to its owner and leaves `dev` and the
    previous release untouched; it never holds the next train.
12. **Never retest what passed.** Every train carries the next JET_VERSION
    bump as its first submission, and its census writes the `Land.jet
    receipt`, so the landed train commit is the release commit and admit
    needs no extra preflight. Admit always runs with `--reuse` naming the
    previous admit's work directory: only rows whose files changed run again.
    Admit's own new work is the fixed point, the pack and the pinned tool
    checks.
13. **No reds reach a train.** Before staging, the worker runs every row its
    `tests` file names on the newest published seed and writes the pass line
    for each in `msg`. A row that needs the submission's own compiler change
    is named as such, and the lander runs those rows first on the train's
    built compiler, returning any red at once. A train that sets a submission
    aside has paid a whole census and test pass for nothing.
14. **Direct lands run the guards they reach.** A direct land runs the
    submission's rows plus every `tests/guards` row whose inputs its paths
    touch, in shards, before it lands. A guard red found on `dev` later is
    a lander defect. A direct that touches `Core/`, `Compiler/` or
    `Tools/agent/` also runs the cheap ratchets of its reach (CoreCoverage,
    CoreSurfaceLedger and DiagnosticRows `--check`) and lands only when
    all pass, so a direct never lands a census red.
15. **The speed gate.** Every train times the seed's `jet build Compiler`
    and the built compiler's self-checks in user plus system CPU seconds,
    with per-phase seconds from the compiler's own trace, beside the
    previous train's row. A rise over 10% fails the train, and the report
    names the phases that grew.
16. **Census by reach, sized to memory.** The census runs check, build and
    the guard shards at once, then self-checks beside the Jetpack areas. It
    runs only the areas a submission's paths reach. The area budget is
    MemAvailable at launch minus 12 GiB, capped at 32 GiB. Each REPORT
    records every phase's seconds.
17. **The latency target is 15 minutes.** Each REPORT records, per
    submission, the minutes from staging to landing, split into inbox wait,
    gate, census, build, tests, set-aside and land. A submission over 15
    minutes names the stage that cost it.
18. **Sweep the cards daily.** Each lane spends 20 minutes a day on every
    open criterion of its goal's cards. It sends the orchestrator `MEET
    #card cN: evidence` for each one already met by the code or an existing
    test, and `DROP #card cN: reason` for each one that's obsolete or
    superseded (not for one that's merely unmet). The orchestrator records
    them in batches.
19. **Speed work names its step.** A speed submission names the step of the
    compile-speed plan it serves (#5479). Until the language is stable,
    architectural steps and regression fixes land, and a gain from tuning
    one function, loop or constant waits.
20. **Express trains and set-aside by reach.** A staged submission enters
    the express queue at once and never waits for a batch. A direct
    submission (docs, tools or tests only, with no `Compiler/`, `Core/`,
    `Jetpack/` or `Examples/` path) runs its own rows and every guard on the
    current train compiler, then lands under the shared land lock. Any other
    submission starts its own one-submission train, with its own build,
    census and rows, and is never held by another owner's red. At most two
    run at once, each only while the declared memory caps leave its census
    inside 40 GiB and MemAvailable minus 12 GiB stays at 16 GiB or more. A
    clean train lands at once. In a multi-submission train, a submission that
    goes red after the build is set aside. If it touched no compiler input,
    the rest lands on the same build. If it did, the tree is rebuilt and
    re-censused by reach (build, guards, self-checks and the Jetpack areas
    its paths reach), never in full, and then the rest lands. Whole-profile
    ui and golden runs are sharded four ways.

`Tools/agent/Land.jet batch` runs rules 1 to 4, 7 and 8 itself: the seed gate
of every touched package from an empty directory, one `precommit`, the
affected rows in memory-sized waves on a sealed export with an immediate
rerun on `HEAD`, the set-aside of a red job (with only the jobs whose patches
no longer apply without it; a negative test fixture is never gated), and the
stage table at the end of `batch-land.log`. Rules 5 and 6 are the lander's
when it cuts and schedules the trains.

## 0. Context the ballot depends on

- D-BUILTIN-METHOD1=A (ratified 2026-11-18) lets an impl name structural heads: `impl [T].SequenceTools` and `impl [T#N].SequenceTools`. It also says: "The canonical built-in family declares its parameter roles/order (T is a type, N a compile-time extent); these names bind in the target exactly as parameters of a nominal conditional impl. Bounds attach to those parameters under D-IMPL-COND1 … Sized lanes and other canonical families use their existing type-head parameter order."
- D-IMPL-COND1=A (ratified 2026-11-10, archived 2026-11-18) gave `impl Pair<T: Priced>.Describe`. Its option B was a trailing `impl Pair.Describe when T: Priced`, rejected as "a second way to write a bound".
- Parser: `parser_parse_impl` (JetParser Items.jet:3119-3152) reads the impl head as a name, then reads `<…>` with `parser_parse_type_params`, the same reader `fn<…>` uses. Sema checks that the list repeats the struct's declared parameter names in order (`sema_registration_impl_conditions_valid`, JetSema Registration/Items.jet:3589-3607). It checks bounds positionally against `.Apply` arguments (`sema_type_impl_conditions_met`, TypeRelations.jet:2546-2561).
- Syntax registry: `<N: Int>` is "compile-time number parameter declaration: a parameter bounded by exactly the core `Int` is a number, not a type" (Spellings.jet:38). Multiple bounds are written `T: [A, B]` (e.g. Tests/Cases/Fmt/FmtPreservesGenericTypeParamBoundList). `?.` is `OP_OPTIONAL_CHAIN` (MathLayout.jet:812-814). `impl Type.Trait using field` already places a clause after the head (MathLayout.jet:754-756).
- Types.jet:33-39: "A written `Option<T>` is the same type" as `T?`, and "A written `Result<T, E>` is the same type" as `T E!`.

## 1. Strongest existing solutions, stated fairly

| Language | Spelling for "every list whose items have P" | Best case | What it does that this design does not |
|---|---|---|---|
| Rust | `impl<T: P> P for Vec<T>`, or `impl<T> P for Vec<T> where T: P`; arrays `impl<T: P, const N: usize> P for [T; N]` | Every parameter is declared in one list before use, so a name in the head is never confused with a type in scope. `const N: usize` declares the number's kind explicitly. | Rust has **two** places for bounds, the `impl<…>` list and `where`, which contradicts the ballot's Rust note. `where` can bound non-parameter types (`where Vec<T>: Debug`). Specialization of overlapping impls is available on nightly. Source: Rust Reference, Implementations §Generic implementations, and Generics §Where clauses, §Const generics (doc.rust-lang.org/reference/items/implementations.html, …/items/generics.html). |
| Swift | `extension Array: P where Element: P`; `extension Optional: P where Wrapped: P`; `extension Dictionary: P where Value: P` | The head is the family's nominal name, and its parameter names (Element, Wrapped, Key, Value) are declared once by the standard library. Nothing repeats and nothing binds fresh. Requirements the type itself states (`Key: Hashable`) are implied inside the extension, which is the rule the ballot wants for map keys. | Same-type constraints (`where Element == Int`) and constraints on associated types. Source: SE-0143 Conditional conformances (github.com/swiftlang/swift-evolution/blob/main/proposals/0143-conditional-conformances.md); The Swift Programming Language, Generics §Extensions with a Generic Where Clause. |
| Haskell | `instance P a => P [a]`; `instance P a => P (Maybe a)`; `instance P v => P (Map k v)` | The head's variables are fresh because they are lower-case, so a variable cannot be mistaken for a type. Haskell 2010 requires an instance head to be a constructor applied to *distinct* type variables: exactly the "fresh, distinct, one family" rule A needs. | `FlexibleInstances` and `OVERLAPPING` pragmas for nested and overlapping heads. Source: Haskell 2010 Report §4.3.2 Instance Declarations (haskell.org/onlinereport/haskell2010/haskellch4.html). |
| Scala 3 | `given [T: P]: P[List[T]] with …` or `given [T](using P[T]): P[List[T]] with …` | Parameters are declared in a list before the head, as in Rust. A context bound is the short form and `using` the long form. Givens are scoped by import. | Prioritized and imported instances, so local overrides are possible. Source: Scala 3 Reference, Contextual Abstractions §Given Instances and §Using Clauses (docs.scala-lang.org/scala3/reference/contextual/givens.html, …/using-clauses.html). |

A has no direct counterpart in another language. No other language names the parameters in the shape and then names them again in a trailing bound list. That is no defect in itself, since A copies Jet's own `Pair<T: P>` position. But the ballot must say so. The languages divide on one property the ballot does not discuss: whether parameters are **declared** (Rust, Scala, Swift's library) or **implicitly fresh** (Haskell by case, A by position). Jet types and parameters are both PascalCase, so A cannot borrow Haskell's case rule (F2).

## 2. Claims and verdicts

### C1. "`impl [T].Describe` stops at the parser … (p1); `impl<T: Describe> [T].Describe` stops the same way (p2); a trailing `where` is refused (p3)"
Reproduced on batch14 (`outputs.txt` p1-p3): the messages are exact. Two limits. The ballot cites `jet a0.0.46#4c75090a92`, while batch14 reports `a0.0.46-dev` (F16). Each probe also produces a second cascade error at the closing `}`: "2 problems found". The repository already requires one refusal with no cascade for foreign impl habits (Tests/UI/impl_generic_head_teaches_bare_type.jet). None of the options says how the *other* options' spellings are refused, such as a Rust habit `impl<T: D> [T].D` under A (F18).
**Verdict: holds within limits.**

### C2. "`[T: Describe]` is already a type spelling" (p4)
p4 prints `#1`, and `[String: Describe]` is a valid map of trait values. In an impl head a partly concrete map head would be illegal anyway, so a resolver could separate the two readings by name kind. Even so, the reader cannot, and C makes the parse depend on name resolution.
**Verdict: holds.**

### C3. "`impl Pair<T: Describe>.Describe` works (p5)" and the quoted Jet.TraitNotImplemented text
Reproduced verbatim, Why line included.
**Verdict: holds.**

### C4. Every option shows the same program, and the results are the same in each
`make.py` builds every option's `code` from one `program(HEADS[key])`, so the bodies and calls are identical. q03b runs all four bodies today as generic functions and prints `[#1, #2]`, `2 items: #3, #4`, `some #5`, `{#6}`, `[]`, `none`, which matches the comments. Limits:
- The last call, `print(["x"].describe())`, makes the whole program fail to build, so none of the five results is ever printed. Move it to a comment or a separate refusal snippet (F11).
- The surface options show 4, 2, 2 and 1 heads for A, B, C and D. The owner sees different amounts of syntax per option (F14).
- The fixed-array body needs explicit type arguments today, because T is not inferred from a `[Int#2]` argument (q02b: Jet.UninferableTypeArgument). That matters for the "generic callers" edge case on fixed arrays (F11).

**Verdict: holds within limits.**

### C5. A: "The length N takes no bound: `#N` already makes it a number, so the list writes it bare. A bound on N is E0003."
This contradicts the syntax registry. In Spellings.jet:38, `<N: Int>` is how a number parameter is declared, and the impl list is read by the same `parser_parse_type_params` as `fn<…>`. q02a: in `fn<T, N>(xs: [T#N]) -> Int { N }` a bare `N` is a type parameter, and reading it gives "Jet.UnknownName: Nothing named `N` exists here". q02b and q02c: `fn<T, N: Int>` reads `N` and prints `2`. A therefore refuses the only number-parameter spelling Jet has, and gives a bare `N` a meaning it has nowhere else. Rust's best case (`const N: usize`) also declares the kind. Fix: `impl [T#N]<T: Describe, N: Int>.Describe`. A bare `N` should be refused with an edit that adds `: Int`. The loss "the bare length N reads densely" then goes away (F1).
**Verdict: fails.**

### C6. A: head parameters are "fresh parameter names"; "It binds head parameters by matching the receiver's shape against the head"
- This conflicts with the ratified text. D-BUILTIN-METHOD1 says the family "declares its parameter roles/order" and the names "bind … exactly as parameters of a nominal conditional impl". Nominal conditional impls bind by the type's **declared** names (Registration/Items.jet:3589-3607). q14 shows the refusal "The conditional impl of `Two` names `<A, A>` … `Two` declares `<A, B>`". "Fresh" names are a different rule, and the ballot does not say it is changing the ratified wording.
- Unbounded heads have no list, so nothing declares the name. `impl [Point].Describe` with a struct `Point` in scope is either a concrete head (illegal) or a blanket impl whose parameter happens to be called `Point`. The ballot does not say which. A blanket impl in that case would silently cover every list.
- The existing mechanism already gets this wrong. q15/q15b: with a struct named `T` in scope, `impl Pair<T: Describe>.Describe` is accepted without any diagnostic, and **neither** `Pair<Int>` nor `Pair<T>` gets `describe` ("Jet.UnknownFunction: `Pair` has no method `describe`"). This is a live defect in the D-IMPL-COND1 implementation and needs a criterion on its owning card.
- Repeated names (`[T: T]`, `[T#T]`), nested or partly concrete heads (`[[T]]`, `[T]?`, `[K: [V]]`) and concrete lengths (`[T#4]`) are excluded by A's grammar sentence, but no refusal text, code or edit is given for them (F10).

B's declared list removes the ambiguity by construction, which is the strongest case for B, and the ballot does not credit it. A can match B only if it pins a rule. Two candidates: canonical family names (T; T and N; K and V), as in Swift and as the ratified text suggests, or "a head name that resolves to a type in scope is a concrete head and is refused". Either way the ballot must say what happens on a collision, for every option (F2).
**Verdict: fails.**

### C7. A: "A map's keys keep the map's own key rule without restating it"
No generic key is a valid map key today, whatever its bound. q09 (`fn<K, V>(m: [K: V])`) and q09b (`K: Equatable`, `K: Comparable`, `K: KeyBy`) all fail with "Jet.InvalidMapKeyType: `K` can't be a map key type". The claim is therefore a new rule, Swift's implied `Key: Hashable`, presented as an existing one. The ballot must name it as new work under every option. It must also say what K supports inside the body (`self.keys()`, lookup), and whether `fn<K, V>(m: [K: V])` gets the same rule. Without that, a generic map impl compiles while the equivalent generic map function is refused (F3).
**Verdict: fails.**

### C8. "One place for impl bounds, for structs and built-in shapes alike" (A's lead gain) and "B/D: two places"
- In both forms the list sits after the head, so the *position* is shared.
- In `Pair<T: D>` the list **is** the head's argument list, and each name appears once. In `[T]<T: D>` the list is a second mention after the shape. The two read differently, and the ballot counts the repetition as a loss.
- Under D-BUILTIN-METHOD1, `Set<E>`, `Shared<T>`, `Task<T>`, `Receiver<T>`, `Sender<T>` and `Result<T, E>` keep their nominal heads. Their bounded form under A would be the Pair argument form, `impl Set<T: D>.D` (q05 is refused today only by Jet.ImplOnBuiltinType). So under A, sigil-headed families use a trailing list and nominal-headed families use argument position. The ballot treats none of these sibling families (F4a).
- Today `Option<T>` is the same type as `T?` (Types.jet:33-35, q18 prints 5 and 6). So `impl Option<T: Describe>.Describe` is the existing Pair form, with no new grammar, no repeated name and no `?.` token. It is not named or weighed. The formatter writes types as `T?` (Formatter/Expressions.jet:758-773), which is a reason to prefer `T?`, but that reason has to appear in the ballot (F4b).
- B's migration cost is stated as "every conditional impl in the tree would change with it". The tree holds seven such sites, all tests: the parser test, two fixture lines and four Tests/UI files. The spec paragraph is also affected. The real cost is reopening the ratified D-IMPL-COND1, and that is what the ballot should say (F4).

**Verdict: holds within limits.** The shared position is real. The single-form claim fails for nominal-headed built-in families and for the optional family.

### C9. "No reading of `[T: Describe]` as a map, and no new keyword"
This holds for A. For B and D it also needs the `?.` caveat. `T?.Describe` lexes `?.` as OP_OPTIONAL_CHAIN (q11 prints `4` for `b?.n`). That token appears in A's own **unbounded** head `impl T?.Describe`, in the ratified unbounded form, and in B's and D's bounded heads. The impl-head parser must split it. The ballot names this for no option (F7).
**Verdict: holds within limits.**

### C10. "The checker's fix writes the head, so beginners never type it from memory" (A's gain, story, technical)
q06: today's nominal analog, a body calling `self.a.describe()` under `impl Pair.Describe`, gives "Jet.MissingGenericBound … Fix: Add `<T: Describe>` to the generic parameter list". That fix comes with **no edit**, and `jet fix --all --dry-run` makes no changes. So the gain is new work for nominal and structural heads alike. Any option can carry the same fix, so it does not separate A from B, C or D and does not belong among A's comparative gains (F5).
**Verdict: fails as a comparative claim. It holds within limits as a requirement on the implementation.**

### C11. "A list with no bound at all is E0003 with an edit that removes it, exactly as `impl Pair<T>.X` is today"
q07: the edit exists, but `jet fix` skips it ("needs review: `jet fix --all` applies it"). Its title reads "Write `impl Pair {`", which drops `.Describe`, although the span edit itself leaves `impl Pair.Describe {`. The header "`impl Pair` takes no type parameters" contradicts the existence of conditional impls. Copying that text "exactly" would make it wrong for structural heads. The ballot also mixes registry codes (E0003, E0908, E0905) with printed names (Jet.TraitNotImplemented). Users see Jet.InvalidStatement, Jet.MissingGenericBound and Jet.TraitNotImplemented (F5).
**Verdict: holds within limits.**

### C12. Edge cases: nested shapes `[[7]]`, generic callers, overlap, empty values
- Nested values: q08 prints `pair pair #7` for `Pair<Pair<Int>>`, so recursive conditional satisfaction works in the nominal analog.
- Generic callers: q08 prints `pair #8` through `fn<U: Describe>(p: Pair<U>)`.
- Overlap: Tests/UI/conditional_impl_overlap.jet pins E0908 for the nominal case.
- Empty values: q03b prints `[]` and `none`, confirming that the bound is checked on the type, not the contents.
- Fixed arrays and lists: q12 shows `[Int#2]` passing where `[Int]` is wanted, and `f.len()` working on it today. Under A's rule, a user's `[T]` trait methods would not exist on fixed arrays, although list built-ins do. That is a beginner surprise, and the ballot names neither its cost nor a mitigation, such as a refusal that teaches `impl [T#N]` or widening (F15).

**Verdict: holds within limits.**

### C13. Expert path: "several bounds, bounds on K and V, generic callers and trait values"
- Several bounds: `T: [A, B]` is the existing spelling (Spellings/Fmt fixtures). q21 runs `impl Pair<T: [Describe, Loud]>.Describe` and prints `pair #1 !1`, so that part holds.
- Trait values: q10 shows `Pair<Describe>{a: 1}.describe()` prints `pair #1`. But q13 shows `[Describe]{1, 2}` passed to `fn<T: Describe>(xs: [T])` fails, with a wrong diagnostic: "No trait named `Describe` is in scope for the bound on `T`". That is exactly the structural trait-value path, and it is unverified and currently broken. It is an existing defect and needs a criterion on the build card (F12).
- Bounds on K: these depend on F3.

**Verdict: holds within limits.**

### C14. C: "Grouping parentheses in types are new syntax"
This is false. q20 compiles `fn(x: (Int | String)?)` and `-> Int (ParseError | TimeoutError)!`, and prints `1` and `2`. The `!` row of Spellings writes `(A | B)!`. What is new in C is a bound *inside* the parentheses, not the parentheses themselves (F6).
**Verdict: fails.** The correction does not rescue C: C still collides with the map reading (C2), and `[T: Describe#N]` and `[K: [V: Describe]]` nest a map spelling inside the head.

### C15. D: "adds a keyword and a second place for impl bounds"
This is true, but it omits the deciding precedent. The owner already rejected the same trailing-clause shape (`when`) in D-IMPL-COND1 as "a second way to write a bound". D's whyNot should cite that ruling. D should also say how a trailing `where` combines with the existing trailing `using field` clause (F9).
**Verdict: holds within limits.**

- The Rust note "Rust has no separate struct-head list, so it has one place" is wrong: Rust has both `impl<T: B>` and `where T: B`.

### C17. Tooling: formatter, LSP, `jet fix`, editor grammars
The ballot names no tooling work beyond fixes. Facts it needs to list as cutover:
- The tree-sitter `impl_block` accepts only a name as head: `_head_name`, Tools/Editors/TreeSitter/grammar.js:237-264. It already admits a prefix `type_parameters`, which is B's shape. The VS Code tmLanguage and Zed grammars need the same change, together with the guard Tests/Cases/Grammar/editor_grammars_match_generated_sections.case.
- `ImplDef.type_name` is a `String`. `sema_type_conditional_impl_head` (TypeRelations.jet:2567-2587) builds the user-facing `impl {type_name}<…>` text from it, and `sema_type_impl_conditions_met` matches only `.Apply` arguments. Structural heads need a typed head instead.
- The formatter's impl-head printer, LSP hover and definition for methods of a structural impl, and a LEXICAL_LEDGER row in Spellings.jet for the new head form (the I7 registry).

These are the same for every option except for the grammar shape, so they do not change the ranking. Leaving them out is still a failed claim under "missing context is a failed claim" (F13).
**Verdict: fails.**

### C18. Whole-mechanism scope (AGENTS.md: "every place the same kind of fact … lives")
The compiler already keeps structural conditional conformances in a hardcoded table, `sema_type_builtin_bound_satisfied` (JetSema TypeRelations.jet:2613-2668). In it, `List`, `Option`, `FixedList`, `Result` and `Tuple` recurse for structural builtin traits, and `Map` is `Equatable` when its key and value are. The spec states the same thing: "a list, fixed list or option is `Printable` when its element is" (spec.md:1061). This is the same kind of fact the ballot introduces syntax for. The ballot must name the table and give its cutover: Core source impls such as `impl [T]<T: Equatable>.Equatable` under the chosen spelling, with the matching rows deleted. Otherwise it must justify keeping the table as kernel (F4c).
**Verdict: fails.**

### C19. Recommendation A is justified
A's position argument is real (C8), and C is correctly ranked last. But A's comparative gains rest on C5 (bare N), C7 (map keys), C10 (a fix any option can have) and C8 (one form, which fails for nominal-headed families and Option). Its strongest competitor's main advantage, declared names (C6), is not credited. Until F1-F5 are resolved, the recommendation is not justified by the evidence presented.
**Verdict: fails.** A may still turn out to be the right recommendation once it pins `N: Int`, a binding rule and the key rule.

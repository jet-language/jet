## #3133: dense enum sets (`Tools/perf/enumset_bench.py`, new)

**Harness.**

- Arms: `rust_native` (u64 mask), `rust_btreeset`, `jet_set_enum` (`Set<Case>`),
  `jet_bits` (`Bits`), `jet_int_mask`, `jet_packed_fields`.
- Sizes: 8/32/64 cases. Masks are dense (hashed) and sparse (at most two bits).
- Phases reported separately: construction, update, membership, setops,
  iteration, conversion.
- Other cells: allocations (LD_PRELOAD `Tools/perf/alloccount.c`), peak RSS
  (`wait4`), binary bytes, and stdout parity against `rust_native`.
- Bit positions are dense declaration indexes.

**Smoke run.** `--samples 1 --rounds 2000 --sizes 8`, the first version, before
the checksum fix.

- Both Rust arms measured and matched each other.
- `jet_int_mask` and `jet_packed_fields` built and ran, but their stdout did
  not match. The checksum used `^`, which in Jet is not XOR. The harness now
  folds with `(check * 31 + x) % 1000000007` in every arm.
- A rerun with the fix (sizes 8,64) was still running at hand-off.

Defects that block the Jet collection arms:

- `Set<E>` in a function taking `&Set<Case>`: `jet build` ICE
  `checked TIR cannot lower to MIR ... clear_bit: missing checked function target Set<Case>::remove`
  (`crates/jet-driver/src/Driver/mod.rs:6546`).
- `Set<Perm>.sort()` on AOT: rustc `E0277 ... Perm: Ord is not satisfied`
  (`jet_set_sort<T: Ord>`); it is an I2 failure. `jet run` of the 200000-round
  `Set<Perm>` workload timed out (>300 s).
- `Set<Perm>.new()` is typed `Set<Int>`, and then `.add(Perm)` fails with
  `E0108`. The workaround is `Set.from([Perm]{})`.
- `Bits` on AOT:
  - rustc `E0308 jet_bit_set_has expected i64, found JetInt`;
  - rustc "cannot find `jet_bitset_remove`" (did you mean `jet_set_remove`).
- `Bits` has no union, intersection or difference. The arm combines per bit.

**Verdict: PARTIAL.**

- Criteria 1 and 3: MET in harness design. The workloads are matched with
  identical ordering, and dense indexes are used rather than wire values.
- Criterion 2: PARTIAL. Every cell is defined, but the Jet collection cells are
  unavailable because of the defects above.
- Criterion 4: MET. No Flags/EnumSet family is proposed, because there is no
  evidence a specialization is justified.
- Criterion 5: NOT MET. The full `--samples 5` run was not completed.

## #3151: enum codec forms (adapters added under `Tools/perf/enum_codec/`)

**Files.**

- `serde_peer/` pins `serde =1.0.228` and `serde_json =1.0.150` in its
  Cargo.toml (Cargo.lock is committed alongside). It builds with
  `cargo --release --offline` into `target-enumcodec/`, and reports `codec_ns`
  plus `allocation_count` from a counting global allocator.
- `serde-adapter.sh` runs that peer.
- `adapter.jet` and `jet-adapter.sh` form the Jet arm.
  - They use only the canonical `json.to_string` / `json.decode<T>`.
  - There is no allocation counter in the Jet runtime (no
    `JET_ALLOC_STATS`), so Jet `allocation_count` is unavailable.

**Serde run.**

  receipt is `~/.cache/jet-luna/perf/enum_codec_serde.json`.
- The 8 unavailable cells are the adjacent form, which is unavailable by
  harness contract. The 9 unsupported cells are encode of
  evolution/unknown/malformed, which cannot be constructed.
- Rounds are 1 (the harness default).

| form | case | op | bytes | allocs | codec median ns |

| external | payload | decode | 17 | 2 | 692 |

The serde peer's "internal" wire (`{"type":..,"value":..}`) is serde's
tag+content attribute. It is the same wire as Jet's `#Discriminant("type")`.

**Jet run: not valid yet.**

- `jet build --release` of the adapter exceeded safe-jet's 300 s limit on the
  first attempt, so every adapter call failed.
- As a result, `enum_codec_jet.json` shows payload cells as `error`, and the
  "rejected" decode cells are adapter failures, not codec verdicts. Do not use
  it.
- A rebuild with `SAFE_JET_TIMEOUT=2400` was in flight at hand-off.

Defects:

- Jet probe on `jet run` (`~/.cache/jet-test-scratch/Closer11/codec/probe.jet`):
  - external, internal and untagged encode give the fixture wires exactly;
  - evolution and malformed decode are rejected;
  - the payload decodes.
- `jet build` of any enum marked `#Discriminant("type")` or `#Untagged` fails
  with ICE `MIR serde attribute has an invalid payload`
  (`crates/jet-codegen/src/Codegen/MIRRust.rs:7150`). So the AOT adapter
  carries only the external form, and `jet-adapter.sh` exits 77 (unavailable)
  for internal, untagged and adjacent.

**Verdict: PARTIAL.**

- Criterion 1: met for serde. The Jet side is pending, and blocked for 2 of 3
  forms by the ICE.
- Criterion 2: met. Versions and settings are pinned in the serde receipt, and
  the evolution and unknown fixtures are kept separate.
- Criterion 3: met. No dependency enters Jet: serde is in a standalone peer
  crate.
- Criterion 4: half met (serde receipt only).

## #3231: collection jobs

**Entry.** Staged at `~/.cache/jet-test-scratch/Closer11/staged/collections-jobs/`
(`entry.json`, `expected.out`, jet/rust/python/c/node).

- It covers:
  - a stable sort by key with ties, on a copy (the input is not mutated);
  - lower bound and presence search;
  - filter/map/group_by;
  - the same pipeline eager versus lazy.
- There is no error path.

All five languages produced `expected.out` byte-for-byte:

- Jet on `jet run` and AOT (`.jet/build/run 200000 | diff` → match);
- rust, c and node by `diff`.

It is **not** in `Tools/gauntlet/entries/`. With the directory present,
`node --test Tools/gauntlet/harness/run.test.mjs Tools/gauntlet/harness/measurement-manifest.test.mjs`
failed 1 of 27 tests: "measurement manifest covers every corpus entry". The
manifest row needs a `loss_owners[name].source` Tower card number, which a
worker cannot mint. Registering it also needs a new matrix cell,
`collections.sort-search-transform` (an owner/Pip decision). The directory was
moved out and the manifest restored, so the suite is back to its prior state.

**Harness run.** `node Tools/gauntlet/harness/run.mjs --entry collections-jobs --runs 5`,
with results at `Tools/gauntlet/results/2026-09-29-collections-jobs.json`.

  But `jet build run.jet` exited 0 and produced

  That binary matches `expected.out`, so this is a harness artifact-discovery

- The interpreter tier was still running at hand-off.
- Source metrics (criterion 2) are in `entry.json` `source_metrics`, counting

## #3245: Core activation (`Tools/perf/core-activation.mjs`, new)

**What it does.** It generates control/import/use programs for json, regex,
time, data and http. For each arm it measures:

- `jet check` wall, and `jet build --release` wall, reported separately as
  compile cost;
- binary bytes, `size -A` sections and `nm --defined-only` symbol count;
- Core modules named in the generated Rust (the reachable-dependency proxy);
- a startup median over 20 runs;
- LD_PRELOAD allocation count and peak live bytes;
- a single `jet run` wall sample.

It then reports import-minus-control and use-minus-control deltas.

**Status.** Launched as
`Tools/agent/jet-env node Tools/perf/core-activation.mjs --out ~/.cache/jet-luna/perf/core-activation.json --samples 20`.
It had not finished at hand-off: 15 AOT builds through the shared safe-jet
slots. There are no numbers to report.

Observed related fact: the generated Rust for a trivial program is about 7 MB
(`mmio_board_write.rs` is 6,830,566 bytes; `probe_heading.rs` is 7,276,865
bytes). So Core source is emitted wholesale before rustc dead-code
elimination, and criterion 4 (no zero-cost claim from DCE) matters here.

**Verdict: PARTIAL.** The harness exists; the run is pending.

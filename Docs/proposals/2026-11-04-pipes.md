# Pipes: reading a flow in the order it runs

Status: superseded in its spelling. D-PIPE1=A (ratified 2026-11-05) kept the
`|>` step and replaced the `it` topic below with `<>`, the value from the line
above: `raw |> String.from_bytes(<>) ?? return fallback`. The built rules are
the D-PIPE1 entry in [the syntax decisions](../spec/syntax-decisions.md); `it`
never names a pipe value. The rest of this document is the 2026-11-04 proposal
as reviewed. The evidence, the census commands and the prior art are in
[the pipes research note](../research/2026-11-04-pipes.md).

Code blocks carry one of three labels in their first line:

- `// today (file:line)` is code on dev at `0d1ea12f79`, quoted as written;
- `// today (probe pN)` or `// today (probe gN)` ran on the admitted
  compiler. Probes p01 to p15 ran on `a32d3791`. Probes p16 to p20 ran on
  `a32d3791` and again on `3993915aeb`, with the same results. The spelling
  probes g01 to g14 ran on `3993915aeb`. The probe files are in
  [the research assets](../research/assets/2026-11-04-pipes/);
- `// proposed A`, `// proposed B`, any other `// proposed …` label and
  `// ratified, not built` mark code that no compiler accepts today.

## 1. Summary

The owner's hunch holds, with one boundary. A pipe does a job that dots and
functions do not do in Jet. It lets a flow read top to bottom when its steps
are not methods. It must not become a second way to call a function.

- About 950 places in the repository read inside out or invent throwaway
  names. Dots cannot fix most of them, because the data goes to a later
  argument, an operand, or a function such as `String.from_bytes`.
- The recommended design is a **topic pipe**: `x |> f(it, 1)`. The value from
  the line above is written as `it`, where it belongs. Every call stays an
  ordinary call.
- `it` is not a new word. Jet already reserves it for **the current
  subject**: the value an arm table or a bindingless loop is about. A pipe
  stage is one more subject, and it follows the same rules.
- In meaning, a pipe stage is a `::` binding named `it` that lives for one
  step. It lowers to exactly that, so it costs nothing and runs the same on
  every tier.
- A formatter rule keeps receiver steps on dots, so a pipe never competes
  with a dot chain.
- No single ASCII character works as the pipe. Backslash is the only free
  one, and it reads as an escape. A leading bar already means "or" at the
  start of a line. The best ASCII spelling is `|>`, in one direction only
  (section 4, "Spelling the pipe in ASCII" and "Direction").

## 2. The problem

### 2.1 Three shapes that read badly today

Counts are from the census on dev at `0d1ea12f79`, excluding the runtime's
raw memory helpers and generated files.

| Shape | Sites | Example |
|---|---|---|
| Calls nested three or more deep | 516 | `hex_encode(slice_u8(sha2_256(bytes, C_SHA224_IV), 0, 28))` |
| Steps alternating between calls and methods | 824 | `provider_toml_quoted(provider_toml_value_without_comment(value).trim())` |
| Three or more `::` lines, each used once by the next | 1,850 | `raw ::`, `text ::`, `port ::`, each ending `?? return fallback` |

Hand checks of 25 samples per shape found about a third clearly better as a
flow. That is roughly 165 nested, 230 mixed and 550 named-run sites: about 950
places, one per five files.

### 2.2 Why dots cannot fix them

A dot chain already reads in order, and the repository has 1,286 of them.
But a step can join a dot chain only if it is a method of the value.

- In 69% of the nested sites and 59% of the mixed sites, some step needs
  more than a dot. It passes the data to a later argument, or calls a type
  or module function such as `String.from_bytes`, `Int.parse` or
  `json.parse`.
- Jet gives each function one call spelling. Those steps will never be
  methods, even when extension methods are built.
- Of the named runs, only 23% pass the value to the receiver or the first
  argument at every step. 45% use it as an operand, as in `x * 8`, and 31%
  pass it to a later argument.

### 2.3 Why names are not free

Named steps read in order, but each name must be new. Jet has no shadowing:

```jet
// today (probe p04): E0118, "The name `x` is already taken here"
fn run() {
    x :: "  7 "
    x :: x.trim()
    print(x)
}
```

So a three-step flow needs three names. Often they repeat the function name
(`bytes`, `text`, `value`) and say nothing more. Half the named runs (910)
also end each step with a fallback, such as `?? return fallback`. Any fix must
keep that per-step fallback.

### 2.4 Where a pipe would make code worse

The census also shows where a pipe does not belong:

- **Existing dot chains.** `xs.filter(…).map(…).sum()` is already in order.
- **Names that carry meaning or are reused.** The IR builder in
  `Compiler/JetIR/Source/BuildLazy.jet:1576-1580` names `one`, `below` and
  `message`; the names document the program it builds.
- **Trees, not chains.** `Err(sema_budget_fail(sema_budget_invalid(name,
  "…", "…", expr_span(expr))))` builds one error from four facts.
- **Address arithmetic.** `rt_text_word(wrapping(values + at * I64{8}))`
  appears 1,722 times in the runtime and is clearer as one expression.
- **Two short steps.** `nixeval_sorted(record.outputs.keys().to_list())`
  reads fine.

## 3. What a pipe would mean in Jet

Each existing form already has its own meaning:

- a **method**, `text.trim()`, is an operation that belongs to the value's
  type;
- a **nested call**, `f(g(x))`, is one expression the reader unwinds from
  the inside;
- a **named step**, `a :: g(x)`, gives a value a name for the rest of the
  block.

A pipe means "take this value through these steps, in this order." The steps
are ordinary calls, written as they are written everywhere else. The only
thing a pipe adds is an unnamed value that lives for one step.

That value already has a name. Jet reserves `it` for **the current
subject**, in two places today:

- in `if subject == { … }`, when the subject is a call or a field rather
  than a plain name, the arms read it as `it` (the spec's "Branching,
  results, and loops");
- in a bindingless loop, such as `loop users if .active -> .name`, the item
  is `it` and a bare `.member` reads it (D-LOOP-SUBJECT1).

In both, the compiler declares a hidden read-only local named `it` for one
scope. No program can declare its own `it`: it is a keyword (E0003, probe
p19). A pipe stage adds a third subject, the value from the line above. It
uses the same hidden local, scoped to the stage.

So a topic pipe is a second **spelling** of a `::` binding used once, read
through the subject word Jet already has. It is not a second mechanism.
Jet's one-mechanism rule lets spelling flex where it helps users; the census
says where it helps. The rule against parallel mechanisms is met by four
facts:

- the pipe lowers to `::` bindings, so there is one semantic path;
- `it` keeps one meaning, the current subject, under the rules that tables
  and loops already follow (section 4, "When subjects meet");
- a call keeps one spelling, `f(it, 1)`, so a search for `f(` finds it;
- the formatter turns a stage that only calls a method on `it` into a dot,
  so a pipe never duplicates a dot chain.

The design climbs the same ladder Jet uses elsewhere. A nested call grows into
a pipe, a pipe grows into named steps, and named steps grow into a function.
Code actions move one rung at a time, and the meaning never changes.

## 4. Alternatives

The same small program runs through every alternative. It is real code
shortened from `Core/Web/Web.jet:374-380` and `Core/Crypto/Crypto.jet:360`.

```jet
// today (probe p12)
fn app_port(raw: [U8], fallback: Int) -> Int {
    text :: String.from_bytes(raw) ?? return fallback
    port :: Int.parse(text.trim()) ?? return fallback
    if port < 1 || port > 65535 -> fallback else -> port
}

fn sha224(bytes: [U8]) -> String {
    hex_encode(slice_u8(sha2_256(bytes, SHA224_IV), 0, 28))
}
```

### A. Topic pipe: `x |> f(it, 1)` (recommended)

```jet
// proposed A
fn app_port(raw: [U8], fallback: Int) -> Int {
    port :: raw
        |> String.from_bytes(it) ?? return fallback
        |> Int.parse(it.trim()) ?? return fallback
    if port < 1 || port > 65535 -> fallback else -> port
}

fn sha224(bytes: [U8]) -> String {
    bytes
        |> sha2_256(it, SHA224_IV)
        |> slice_u8(it, 0, 28)
        |> hex_encode(it)
}
```

**Meaning.** `head |> stage` evaluates `head`, then evaluates `stage` with
`it` bound to that value. The result is the stage's value. Each further
`|> stage` takes the result of the one before. It is exactly:

```jet
// proposed A: what the first function lowers to
fn app_port(raw: [U8], fallback: Int) -> Int {
    it_1 :: String.from_bytes(raw) ?? return fallback
    port :: Int.parse(it_1.trim()) ?? return fallback
    if port < 1 || port > 65535 -> fallback else -> port
}
```

`it_1` stands for the hidden local, the same kind a table declares for its
subject.

**Precedence and associativity.** `|>` is left-associative and binds more
loosely than every other operator, including `??`, `||` and `==`. A head and
each stage end at the next `|>`. A keyword such as `return` or `panic`
inside a head or a stage takes its operand only up to that `|>`. So:

- `x |> f(it) ?? return d |> g(it)` means `(x |> (f(it) ?? return d)) |>
  g(it)`. The fallback belongs to its own stage, as in a named run.
- `return x |> f(it)` returns the whole pipe, and `y :: x |> f(it)` binds it.
- A fallback for the whole pipe is one more stage: `x |> f(it) |> g(it) |>
  it ?? d`. It handles only the last value, exactly as `?? d` on the last
  named step would.
- A line that starts with `|>` continues the line above, under the same rule
  as a leading `.` or binary operator.

**Argument placement.** `it` goes wherever the value belongs: the first
argument, a later one, a receiver inside the stage (`Int.parse(it.trim())`),
an operand (`it * 8`), a field (`Point{x: it, y: 0}`) or a string
(`"{it}"`). A stage may use `it` more than once; it is one value, like a
name.

**`?` and effects.** A stage is an ordinary expression, so nothing new
applies:

- a failing call in a stage leaves the function, like any failing call;
- `?("note")` adds a note to that stage's failure;
- `?? fallback` and `?? return value` handle that stage only, and the
  fallback can read `err` and `it`;
- the pipe's effects are the effects of its stages, as for statements;
- Jet has no `await`, so there is no await rule.

**Where a pipe may stand.** A pipe may be a whole statement or the value of a
binding or assignment. It may also be the operand of `return` or `break`, or
the last expression of a braced block or a lambda body. Anywhere else, such
as a call argument or an `if` condition, it is an error that asks for a name
first. This keeps the lowering exact: the stages become `::` lines just
before the statement, and nothing else in that statement runs between them.

**Ownership and lifetime.** `it` follows the rules of a `::` binding. It is
read-only, so `&it` is the same error as writing through any `::` binding.
Each stage's value lives exactly as long as the named step it replaces, so a
view taken in one stage stays valid in the next. Stages run top to bottom,
the order of named steps.

**When subjects meet.** A pipe stage can sit near a table or a loop that
also has an `it`. Today's rules for a second `it` come from probes p16 to
p20, run on `a32d3791` and `3993915aeb` on 2026-11-04:

| Today | Which `it` the inner code sees | Probe |
|---|---|---|
| A table over a call or a field | The table's subject | p16 |
| A table over a plain name, such as `if n == { … }` | None; reading `it` is E0107 | p18 |
| A table inside an arm of a table over a call | The inner subject hides the outer one | p16 |
| A table on `it` itself, inside such an arm | A plain-name table, so its arms keep the outer `it` | p20 |
| A table whose subject reads `it`, such as `if (it ?? 0) * 10 == { … }` | The subject reads the outer `it`; the arms see the new one | p20 |
| A bindingless loop inside an arm of a table over a call | E0118, "The name `it` is already taken here" | p17 |
| A bindingless loop inside a bindingless loop | E0118, and E0380 "This loop needs a named source binding" | p18 |
| A table over a computed value, such as `if .age * 2 == { … }`, inside a bindingless loop body | The arms see the loop item, not the table's subject | p16 |

The last row contradicts the spec, which says the arms read the table's
subject. It looks like a bug; the research note reports it.

So Jet already has two kinds of subject. A table's subject **hides** an
outer `it` inside its arms. A loop item **refuses** to open while another
`it` is visible. A pipe stage is a flowing value, like a loop item, so it
takes the loop rule. Tables keep theirs. Exactly:

| Proposed A | Rule |
|---|---|
| A pipe inside an arm of a table over a call or a field | E0118, with a note naming the table's line. Fix: name the subject first, as in `found :: find(xs, 5)` and then `if found == { … }`. Those arms have no `it`, so the pipe is legal. |
| A pipe inside an arm of a table over a plain name | Legal, because no `it` is visible. |
| A pipe inside a bindingless loop body, including a lambda there | E0118, as for a nested loop. Fix: name the item, as in `loop u in users -> …`. |
| A pipe inside a stage, which can only happen in a lambda or a block there | E0118. Fix: "Name this stage", or move the inner steps into a function. |
| A pipe in a lambda inside the head | Legal. The head runs before any stage, so no `it` is visible. |
| A table on `it` inside a stage, or as the whole stage | A plain-name table, so its arms keep the stage's `it`. |
| A table on any other subject inside a stage, or as the whole stage | Its subject reads the stage's `it`. Its arms see the table's subject as `it`, as today. |
| A bindingless loop inside a stage | E0118, as in p17. A named loop is legal: `\|> loop u in it.users -> u.name`. |

A stage that is a table looks like this:

```jet
// proposed A
fn first_five(raw: [U8]) -> Int {
    raw
        |> decode(it) ?? return -1
        |> if find(it, 5) == {
            .Val(i) -> i
            else -> -1
        }
}
```

`find(it, 5)` reads the stage's value. Inside the arms, `it` would be the
result of `find`, as in any table over a call. Three consequences follow:

- the table-in-loop bug must be fixed first, so that every table follows
  the hiding rule;
- a pipe never meets a bindingless loop, so a bare `.member` never has two
  possible subjects;
- inside a stage, a bare `.member` keeps its ordinary meaning and never
  reads the stage's value. Only `it` does.

The formatter and the code actions respect these edges:

- The formatter never adds or removes a pipe, so it has nothing to refuse.
  Its one rewrite applies only to a stage that is a method call on the
  stage's own `it`. An `it` inside a table's arms never qualifies.
- "Turn into a pipe" is not offered where an `it` is visible, or when a
  moved step contains a bindingless loop. In an arm of a table over a call,
  it offers "Name the subject" first.
- "Name this stage" and "Inline the pipe" rewrite only the `it`s that
  belong to that stage. An `it` inside a table's arms belongs to the table
  and stays as written.

**Generics, overloads and compile time.** Each stage is checked after the
one above, with `it` already typed, exactly as successive statements are.
So `|> f(it)` never needs the type arguments a library helper needs (probe
p08, E0904). Jet has no overloading, so there is nothing to choose between.
A pipe in compile-time code folds like the named steps it lowers to.

**Diagnostics.** The existing errors keep their codes and add the stage. A
type mistake in stage 3 reads:

```text
// proposed A
Error [jet.BindingTypeMismatch]: This needs String, but `it` is [U8]
  --> app.jet:4:18
    |
  2 |         |> load(it)
  3 |         |> check_size(it, 4)
  4 |         |> Int.parse(it) ?? 0
    |                      ^^ `it` here is the [U8] made by line 3
 Why: Each stage receives the value of the stage above as `it`
 Fix: Turn the bytes into text first, with a stage such as
      `|> String.from_bytes(it) ?? return 0`
```

Today the same mistake points into the middle of a nested line, with no hint
of which step made the value (probe p14). New errors cover the new rules:

| Mistake | What the error says | Fix it offers |
|---|---|---|
| A stage never uses `it` | "This stage never uses `it`, so the value from line N is dropped" | Pass `it` where the value belongs, or end the pipe on line N |
| `it` where nothing is the subject | E0107, as today. New reason: "`it` is the subject of a table, a loop or a pipe stage, and none is open here." | Name the value with `::`, or start a pipe. Today's fix suggests `it :: …`, itself an error (E0003, probe p19). |
| A pipe or a bindingless loop where `it` is already the subject | E0118, "The name `it` is already taken here." A note names the line that opened `it`. | Name that subject first, or name the loop item. |
| A lambda as the whole stage | "This stage makes a function but never calls it" | Call it, or write the call with `it` directly |
| A pipe inside a larger expression | "A pipe must be a whole statement or a whole value" | Name the pipe's value first, then use the name |

**Formatter.** One stage per line, with `|>` leading and indented one step.
A pipe with one short stage may stay on one line. The formatter never turns
nesting or names into a pipe, or back. It does one rewrite: a stage that only
calls a method on `it`, such as `|> it.trim()`, joins the line above as
`.trim()` when that needs no parentheses. A lint with the same safe fix
explains why: "This step is a method on the value. Write it as a dot."

**Language server.**

- Hover on `it` shows its type and the line that made it.
- Go to definition on `it` jumps to the stage above.
- Type hints can show each stage's type at the end of its line.
- Completion after `|> ` lists functions that take `it`'s type in any
  position, and places `it` in that slot. Free functions become as easy to
  find as methods.
- Code actions: "Turn into a pipe", from nesting or a named run; "Name this
  stage", which splits the pipe at a stage into `name :: …`; and "Inline the
  pipe". A rewrite that would reorder side effects is not offered (see edge
  cases).

**Debugging.** Each stage is its own line and its own statement in the line
table.

- A breakpoint can stop at any stage, and "step over" moves one stage at a
  time.
- The locals view shows `it` with the current stage's input.
- A failure report names the stage's line, not the whole pipe.

F# lacked this for fifteen years and added it in F# 6; Jet should ship with
it.

**Performance and tiers.** The pipe lowers to `::` bindings before type
checking. The IR is the IR of the named steps, at O0, O1 and O2. There is no
closure, no extra call and no copy at any level. Every tier sees one meaning
because the lowering happens before any tier exists. A paired test proves
it: a pipe and its named form must produce the same IR on every level.

**Beginner path.** Taught after `::` and nested calls, in two sentences:
"`|>` passes the value on its left to the next step. In that step, `it` is
that value." The errors teach the rest. A beginner who never writes a pipe
loses nothing.

**Expert path.** The same. There are deliberately no variants: no reverse
pipe, no composition operator, no partial application, no `tap`, no error
pipe, no placeholder other than `it`.

**Edge cases.**

- **Reordered side effects.** Nesting runs a call's earlier arguments first:
  `wrap(note("outer"), wrap(note("inner"), "x"))` prints `outer` then
  `inner` (probe p13). A pipe runs top to bottom. The "Turn into a pipe"
  action is offered only when the arguments it moves past have no effects.
- **Methods.** `|> it.m()` is legal, and the formatter rewrites it to a dot
  where that is clean. When the previous stage ends in a fallback,
  `|> it.list() ?? return false` stays, because `(… ?? return false).list()`
  is worse.
- **Lambdas.** A lambda inside a call is bounded by the call's parentheses.
  A bare lambda as a stage never uses `it` and is an error.
- **Lambdas that capture `it`.** In `|> words.filter((w) -> w.len() > it)`,
  the lambda captures the stage's value, as any lambda captures a local.
- **Pipes inside lambdas in the head.** `xs.map((s) -> s |> parse(it)) |>
  sum(it)` is fine: the inner `it` ends before the outer stage starts.
- **A pipe inside a larger expression.** `print(x |> f(it))` and `if x |>
  f(it) == { … }` are errors with the fix "name the pipe's value first". In
  the second, the arms would otherwise land inside the last stage.
- **Writes.** A stage can write elsewhere: `|> pkg_bind_unique_name(&used,
  it)`. It cannot write through `it`.
- **No new word.** `it` is already a keyword, so no program can have a
  local, parameter or field named `it` (E0003, probe p19). No existing
  program breaks. On dev at `3993915aeb`, no tracked `.jet` file reads `it`
  in code (0 of 18,019), so the edge rules above change no existing code.

**Spelling.** This section writes the pipe as `|>`. Section 4 tests every
single-character ASCII spelling and both directions, and explains why `|>`,
in one direction, is the best spelling.

### B. First-argument pipe: `x |> f(1)` means `f(x, 1)`

This is the Elixir and Gleam design.

```jet
// proposed B
fn app_port(raw: [U8], fallback: Int) -> Int {
    text :: raw |> String.from_bytes() ?? return fallback
    port :: text.trim() |> Int.parse() ?? return fallback
    if port < 1 || port > 65535 -> fallback else -> port
}

fn sha224(bytes: [U8]) -> String {
    bytes
        |> sha2_256(SHA224_IV)
        |> slice_u8(0, 28)
        |> hex_encode()
}
```

- **Precedence and associativity:** as in A.
- **Argument placement:** first only. A method step must leave the pipe, as
  `app_port` shows. A later argument needs a lambda and a helper,
  `|> apply<String, String>((v) -> wrap("outer", v))`, with the type
  arguments probe p08 shows are needed.
- **Fit:** the census finds the data first at every step in 31% of nested
  sites, 41% of mixed sites and 23% of named runs.
- **`?` and effects:** as in A, per stage.
- **Generics, overloads, compile time:** as in A. Inference is the same,
  except that the hidden argument must be matched to the first parameter
  before the written ones.
- **Diagnostics:** argument errors must explain an argument nobody wrote. A
  stage-3 mistake reads "`Int.parse` needs a String as its first argument,
  but the pipe passes the [U8] from line 3". A count error reads "`slice_u8`
  takes 3 arguments: the pipe gives 1 and this call writes 1".
- **Formatter:** one stage per line.
- **Language server:** signature help must shift every parameter by one
  inside a stage. A search for two-argument calls of `f` misses `|> f(a)`.
- **Debugging:** as in A, except there is no name to inspect; the debugger
  must invent one.
- **Performance:** lowers to the same named steps; zero cost on every tier.
- **Beginner path:** `f()` after `|>` has one argument, and `f(a)` has two.
  That is a second way to call every function, the objection Jet already
  raised against calling free functions with a dot.
- **Expert path:** pressure to put the data first in every function, and
  then to add `then` and `tap` helpers, as Elixir did in 1.12.
- **Edge cases:** a function with no parameters cannot be a stage, and
  `|> f` without parentheses is either an error or a third form.

### C. No new syntax: names, nesting and extension methods

Keep today's forms. When extension methods are built, helpers whose first
parameter is the data can move onto the type, and chains become dot chains.

```jet
// today (probe p12)
fn sha224_named(bytes: [U8]) -> String {
    digest :: sha2_256(bytes, SHA224_IV)
    hex_encode(slice_u8(digest, 0, 28))
}
```

```jet
// ratified, not built: extension methods on [U8] declared in this module
fn sha224(bytes: [U8]) -> String {
    sha2_256(bytes, SHA224_IV).slice_u8(0, 28).hex_encode()
}
```

- **Precedence, placement, `?`, effects, generics, compile time:** today's
  rules. A fallback with `return` can already sit inside a call:
  `Int.parse((String.from_bytes(raw) ?? return fallback).trim()) ?? return
  fallback` runs (probe p10).
- **Fit:** extensions can reach the 159 nested and 336 mixed sites whose data
  goes first through free functions. Type functions, module functions, later
  arguments and operands stay as they are.
- **Diagnostics:** today's. A stage-3 mistake points into the nested line
  (probe p14).
- **Formatter and language server:** today's. A "Name this step" code action
  could help nesting without syntax.
- **Debugging:** named steps stop per line; nesting is one line.
- **Performance:** today's.
- **Beginner path:** nothing new to learn. Inside-out reading and invented
  names stay.
- **Expert path:** turning a helper into a method changes it for every
  caller, so it is a design choice, not a local fix.
- **Edge cases:** a method added only to make a chain read well is an API
  decision made for layout reasons.

### D. A library helper: `apply(value, step)`

A Core function such as `fn apply<T, U>(value: T, step: fn(T) -> U) -> U`.

```jet
// today (probe p15)
fn apply<T, U>(value: T, step: fn(T) -> U) -> U { step(value) }

fn port(text: String) -> Int {
    n :: apply<String, Int>(text, (s: String) -> Int.parse(s) ?? return -1)
    n + 1000
}
```

- **Placement:** anywhere, through the lambda.
- **`?` and control flow:** `return` inside the lambda leaves the lambda, not
  the function. `port("x")` prints 999, not -1 (probe p15). The per-step
  early return that 910 named runs use cannot be written.
- **Generics:** an untyped lambda cannot fix `U`. `apply("  hi  ", (s) ->
  s.trim())` is E0904, and so is a typed lambda ending in `?? return`.
- **Diagnostics:** errors point into lambda bodies and generic arguments.
- **Formatter, language server:** nothing special.
- **Debugging:** each step is a call through a function value, with its own
  frame.
- **Performance:** a call through a function value per step. O0 does not
  promise to remove it.
- **Beginner and expert paths:** lambdas and generics before the first
  pipeline.
- **Edge cases:** effects of the lambda must be allowed by `apply`'s
  signature.

### E. Do nothing

Keep today's language, with no code actions and no guidance. Every dimension
is today's. The cost is the 950 sites: inside-out reading, invented names,
and errors that point into nested lines.

### Spelling the pipe in ASCII

On 2026-11-04 the owner asked for a single-character pipe, in ASCII only.
The lexer gives a meaning to every printable ASCII punctuation character
except backslash and backtick, and backtick opens raw text. So one character
can come only from backslash, or from reusing a character by its position.
Every candidate was probed on `3993915aeb`:

| Candidate | What today's compiler does (probe) | Verdict |
|---|---|---|
| `>` leading a continuation line | Compiles as a comparison. `y :: x`, then `> double(x)` on the next line, prints `false` (g03) | Not viable: valid code would silently change meaning |
| Backtick | Opens raw text: E0002, "This raw text never gets a closing backtick fence" (g05) | Not viable |
| `~` | E0003 between values (g06). But `~x` still teaches the retired copy spelling (E0941), and `~~` the retired method connector (E0325) | Not viable: it collides with live teaching errors |
| `\|` between values | E0003 (g02) | Free in a value, but the same glyph means "or" in patterns and types |
| `\|` leading a continuation line | E0003 after a statement (g01). In an arm head it already continues an or-pattern: `.Red`, then `\| .Green -> true`, runs (g11) | Possible by position, but one glyph would mean "or" and "then" in the same table |
| Backslash, between values or leading a line | E0001, "The character `\` doesn't mean anything here (yet)" (g04, g14) | The only free character |
| `\|>`, two characters | E0003 at the `\|` (g13, and p01 on `a32d3791`). No valid program contains it | Free as a new token |
| `then`, a word | An ordinary name today: 188 code lines use it, 154 of them as a `.then(…)` method call | Needs a keyword or a contextual rule |

The strongest single characters are backslash and a leading bar. Here is
one real site, `Core/Crypto/Crypto.jet:360`, in each:

```jet
// proposed: backslash
fn sha224(bytes: [U8]) -> String {
    bytes
        \ sha2_256(it, C_SHA224_IV)
        \ slice_u8(it, 0, 28)
        \ hex_encode(it)
}
```

```jet
// proposed: leading bar
fn sha224(bytes: [U8]) -> String {
    bytes
        | sha2_256(it, C_SHA224_IV)
        | slice_u8(it, 0, 28)
        | hex_encode(it)
}
```

```jet
// proposed: |>
fn sha224(bytes: [U8]) -> String {
    bytes
        |> sha2_256(it, C_SHA224_IV)
        |> slice_u8(it, 0, 28)
        |> hex_encode(it)
}
```

The leading bar's problem shows inside a table. Line 3 below means "or",
and line 5 means "then":

```jet
// proposed: leading bar, inside a table
if c == {
    .Red
    | .Green -> color_name(c)
        | upper(it)
    else -> "other"
}
```

How each one is typed, read, formatted and diagnosed:

- **Backslash.** One key on US and UK keyboards, and AltGr with another key
  on German and French ones. Readers know it as the escape in `"\n"`, the
  line-continuation mark of shells and Python, and the lambda of Haskell.
  None of those means "pass along". A Jet file would use `\` for escapes
  inside strings and for stages outside them. The formatter would lead each
  stage line with `\`. Today's E0001 would give way to the stage errors. A
  `\` at the end of a line, the shell habit, would need its own teaching
  error.
- **Leading bar.** One key on US keyboards. Shell users read `|` as a pipe,
  which helps. But July's ruling made bars mean alternatives, and Jet uses
  them that way in or-patterns and in types such as `Int | String`. At the
  start of a line in a table, the bar would mean "or" in a head and "then"
  in a body. Indentation would be the only visual cue. A one-line form is
  impossible, because `x | f(it)` reads as "x or f(it)".
- **`|>`.** Two keys, on every layout that has `|`. Readers of F#, OCaml,
  Elm, Elixir, Gleam, R, PHP 8.5 and the JavaScript proposal already know
  it. Coding fonts with ligatures, such as Fira Code, draw it as a single
  triangle. The formatter rules are those of option A. A lone `|` in a value
  gets the teaching error "Did you mean `|>`?".
- **`then`.** Reads as English, but `x then f(it)` also reads like the
  start of an `if`. Making it a keyword breaks the 154 `.then(…)` calls, so
  it would have to be contextual, like `uninit`.

**Finding.** No single ASCII character is truly viable. Backslash is free
but tells a reader nothing and already means "escape". A leading bar looks
like a shell pipe but already means "or" at the start of a line (g11). The
best ASCII spelling is `|>`: free today, one token apart from `|`, and known
from eight languages.

### Direction

A pipe can push right, `x |> f(it)`, or left, `f(it) <| x`, as in F# and
Elm. Today `<|` is E0003, "Expected a value, found `|`" (g12), so it is
free too. Two census sites in each direction:

```jet
// proposed: right push (Core/Crypto/Crypto.jet:360)
digest :: bytes
    |> sha2_256(it, C_SHA224_IV)
    |> slice_u8(it, 0, 28)
    |> hex_encode(it)
```

```jet
// proposed: left push (Core/Crypto/Crypto.jet:360)
digest :: hex_encode(it)
    <| slice_u8(it, 0, 28)
    <| sha2_256(it, C_SHA224_IV)
    <| bytes
```

```jet
// proposed: right push (Jetpack/PackageModel/Source/Foreign/C/HeaderParser.jet:53)
jet_name :: seed
    |> pkg_cbind_trim_end_matches(it, "_t")
    |> foundation_generated_type_name(it, "CRecord")
    |> pkg_bind_unique_name(&used_names, it)
```

```jet
// proposed: left push (Jetpack/PackageModel/Source/Foreign/C/HeaderParser.jet:53)
jet_name :: pkg_bind_unique_name(&used_names, it)
    <| foundation_generated_type_name(it, "CRecord")
    <| pkg_cbind_trim_end_matches(it, "_t")
    <| seed
```

**What left push buys.** The outermost call comes first, so the reader
learns what the result is before how it is made. That is real for short
flows such as `hex_encode`. Elm uses `<|` mostly to drop the parentheses
around a last argument.

**What it costs under the one-mechanism rule.** Two orders would spell one
meaning:

- `it` would mean "the line above" in one form and "the line below" in the
  other;
- stages would run bottom to top, so breakpoints, stepping and error lines
  would move upward;
- a per-stage fallback, as in `__app_port`, would run in the opposite order
  to reading;
- nesting already reads outer call first, so a left pipe repeats what
  nesting says.

**Formatter.** It could normalise `<|` into `|>`, but then `<|` is a typing
alias that no reader ever sees, which is a second spelling for nothing. Or
it could keep both, so every reader and tool must handle two forms. Mixing
directions in one pipe would be an error either way.

**Prior art.** F# and Elm ship both directions, and Raku has `<==` beside
`==>`. Elixir, Gleam, Hack, PHP 8.5, R and the JavaScript proposal ship only
the right push. OCaml pairs its `|>` with a separate application operator,
`@@`, not a mirrored pipe.

**Finding.** One direction only, pushing right with `|>`. `<|` gets a
teaching error: "Jet pipes run one way. Write `x |> f(it)`."

## 6. Recommendation: A, with its downsides removed

| Downside | How the design removes it |
|---|---|
| Two layouts for a single-use value: a name or a pipe | Both are one mechanism, since the pipe lowers to the binding. Code actions move between them, and the formatter never forces either. |
| A pipe could duplicate a dot chain | The formatter rewrites a method-only stage to a dot. |
| A pipe could become a second call spelling | The value is always written as `it`, so every call keeps its one spelling and stays searchable. |
| Precedence surprises, as in PHP's errata and Elixir's warnings | `\|>` binds loosest, and stages end at the next `\|>`. Lambdas stay inside call parentheses. A pipe stands only where a whole value goes. |
| A new word, `it` | Not new. `it` is already Jet's keyword for the current subject of a table or a loop. A stage follows the loop rule, and no tracked file reads `it` in code today. |
| Opaque debugging, as in F# before version 6 | One line and one statement per stage; `it` shows in the locals view; failures name the stage line. |
| Hidden cost | Lowering happens before type checking; a paired test proves identical IR at O0, O1 and O2. |
| Variant creep: tap, error, async and reverse pipes | None are proposed. `?`, `?(note)` and `??` already work per stage. |
| Reordered side effects when converting nesting | The conversion action is offered only when no moved argument has effects. |
| Bars were reserved for alternatives | `\|>` is one token, distinct from `\|`, and a lone `\|` in a value stays an error. The single-bar spellings were probed and rejected because the bar already means "or" (section 4). |

## 7. Relation to earlier decisions

These decision records are cited so Tower can link them:

- **D-SHAPE-PIPE1 (C, ratified 2026-07-14)** ruled that bars mean
  alternatives only, with no general flow operator. Its lesson said a value
  pipe repeats dot chaining. The census contradicts that for Jet: 69% of
  nested and 59% of mixed sites cannot be dot chains. Option A amends this
  ruling. Its warning against tap, error, async and mutation variants is
  kept.
- **D-UFCS1 (B)** rejected a pipeline as "a third call spelling". That
  objection applies to option B. Option A keeps one call spelling.
- **D-CALL-ONE1 (A)** gives each function one call spelling and lets any
  module declare extension methods. It is the basis of option C and is not
  yet built (probes p02 and p07).
- **D-CAP10** rules out overloading, so a stage never chooses between
  definitions.
- **S6-R** makes a leading binary operator continue the previous line. `|>`
  joins that set.
- **D-LOOP-SUBJECT1 (A)** made the item of a bindingless loop the implicit
  subject, written `it`, and taught named bindings for nested loops. Option
  A extends that subject to pipe stages under the same nesting rule.
- The spec's rule that a table over a call reads its subject as `it`
  predates the decision log. Option A keeps it unchanged, including the way
  an inner table hides an outer `it`.
